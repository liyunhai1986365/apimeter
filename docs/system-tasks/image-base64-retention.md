# 任务图片 base64 保留 24 小时

状态：已实现代码及本地验证，尚未部署或启用生产清理。更新于 2026-09-06。

用户要求：只保留最近 24 小时的图片 base64，自动清理过期图片内容；保留任务及相关记录；任务列表和查询接口明确显示“图片已过期”。

## 行为约定

图片结果首次生成完成并持久化后保留 86,400 秒。重复查询、轮询和其他任务字段更新均不延长保留期。使用服务端 UTC Unix 时间计算，页面按用户时区展示。

| 场景 | 数据库 | 任务列表和接口 |
| --- | --- | --- |
| 图片未到期 | 保留原 base64 | 正常查看，可显示到期时间 |
| 图片刚到期，后台尚未清理 | 后台待清理 | 立即显示“图片已过期”，禁止返回过期图片内容 |
| 图片已清理 | 移除图片 base64，保留图片占位信息、任务及其他字段 | 显示“图片已过期” |
| 任务仍在提交、排队或执行 | 不清理执行所需的数据 | 保持原有进行中状态 |
| 只有普通 HTTP 图片地址 | 不纳入 base64 保留策略 | 保持原行为 |
| 视频、音频、文字结果 | 不纳入图片清理 | 保持原行为 |

任务执行状态和图片是否过期分开表达。成功任务过期后仍是 `SUCCESS` / `succeeded`，不会变成失败、触发退款或重新结算。任务 ID、模型、用户、令牌、时间、费用、usage、错误、账单、钱包流水和退款记录均保留。

定时清理每分钟运行。访问期限严格按时间判定，物理清理在正常运行时通常延迟约一分钟；调度延迟和历史积压可能增加物理清理延迟。不能把“一分钟轮询”描述为数据库在第 86,400 秒精确删除。

## 当前代码中必须覆盖的路径

| 位置 | 当前行为 | 需要的改动 |
| --- | --- | --- |
| `service/system_task.go`、`model/system_task.go` | 主节点调度，数据库租约避免同类任务重复执行 | 复用框架注册 `task_image_base64_cleanup` |
| `relay/image_task_handler.go` 的 `finishLocalImageAsyncTask` | 将完整图片响应写入 `tasks.data` | 首次写入图片时固定到期时间 |
| `service/task_polling.go` 的 `updateImageSingleTask` | 原样保存上游图片结果 | 同样设置期限；不能依赖当前始终存在 `finish_time` |
| `relay/image_task_handler.go` 的 `ImageTaskFetch` | 部分任务重新请求上游，部分把 base64 转存为 URL | 鉴权后、请求上游和转存图片前检查是否过期 |
| `relay/relay_task.go` 的实时查询、保存和 DTO 转换 | 部分可配置任务查询会回写结果 | 对识别出的图片任务统一进行过期检查和防回写处理 |
| `controller/task.go`、`model/task_log.go` | 列表省略大字段，详情读取完整保存结果 | 列表返回轻量到期字段；详情执行相同的过期策略 |
| 两套前端任务列表、详情、图片预览 | 按返回内容决定预览 | 识别过期状态，显示统一文案 |

所有入口复用同一个图片保留策略，不能只给后台清理任务加逻辑。尤其不能在清理后又从上游获取图片、重新落库或生成新的 R2 URL。

## 存储字段与并发控制

在 `tasks` 添加普通整数列，兼容 SQLite、MySQL 和 PostgreSQL：

| 字段 | 用途 |
| --- | --- |
| `image_base64_state` | `0` 待识别、`1` 无目标图片内容、`2` 有待保留的内容、`3` 已清理 |
| `image_expires_at` | 图片到期的 Unix 秒，0 表示尚未建立期限 |
| `image_base64_cleared_at` | 实际清理时间，0 表示未清理 |
| `image_base64_version` | 每次图片内容或保留状态变化递增，用于条件更新 |
| `image_has_url` | 标记混合结果仍有普通图片地址，让轻量列表区分全部和部分过期 |

建立 `(image_base64_state, image_expires_at, id)` 组合索引。列表直接读这些小字段，不读取或解析 `data`、`private_data` 大字段，不恢复此前的大响应问题。

新图片第一次持久化时设置 `image_expires_at = now + 86400`，之后不可被旧内存对象覆盖或刷新期限。所有图片结果写入都经过统一的条件更新入口，匹配版本和原有任务状态；清理只更新图片内容、保留字段及版本，不使用整个任务的 `Save`。

仅按 `status = SUCCESS` 做条件更新不足以保护图片清理：两个请求都可能拿着成功状态，后写的旧对象会把 base64 写回来。独立版本号必须贯穿本地图片 worker、图片轮询、实时查询回写及适用的批量写入入口。版本冲突后重读并重新判断，不能直接重试旧载荷。

## 内容清理规则

通过已知图片响应结构定位内容，覆盖标准 `data.images[]`、OpenAI 图片数组、已支持的 Gemini 图片 inlineData，以及已支持的配置化图片响应路径。支持 `b64_json`、已支持的 base64 别名和 `data:image/...;base64,...` 图片地址。

仅移除确认属于图片的编码值，保留外层 JSON、图片数量、文件名和占位对象。图片占位对象增加 `image_expired: true`。不能递归删除所有名为 `data` 的字段，也不能以 `platform=24` 或 `action=generate` 作为唯一图片判断依据。

若 `private_data.result_url` 保存的是同一张图片的 data URI，同步移除该值，保留私有字段中的令牌、上游任务 ID 和计费快照。普通 URL 不从数据库删除。一个结果混有 URL 图片和 base64 图片时，只给被清理的图片标记过期，保留仍可用的 URL 图片；响应可表示部分过期。

终态任务中遗留的图片请求 data URI 也按已识别请求结构清理，保留文本和参数；这类输入清理不把“没有生成图片”的失败任务标成成功结果已过期。未完成任务的请求快照交由已有超时机制先转入终态，清理任务本身不改变其执行状态。

JSON 处理使用 `common` 包的封装。对无关字段保留原始 JSON 值，避免通过 `float64` 往返导致整数精度变化。无法识别或解析的数据保留原值、记录失败并告警，不能把整段结果置空。

## 调度和历史回填

新增一个 `ScheduledSystemTaskHandler`，间隔一分钟，复用数据库单实例租约、续租、取消和运行记录。当前生产的 slave 不执行系统任务，主节点停机期间会延迟物理清理，恢复后继续；各节点的读取过期检查始终生效。

每轮先用索引取最多 50 个到期任务的轻量信息，再逐条读取和处理内容。每轮最多处理 1,000 条或运行 45 秒，先到即结束；限制并发为 1，检查 context 取消，避免一次把几十张大图加载进内存或开启长事务。积压留到下一轮。

单条清理使用条件更新：目标仍处于终态、版本未变化、到期时间未变化、尚未清理。记录处理条数、实际移除的 JSON 字节数、失败条数、耗时和最老待清理时间；记录中不包含图片、请求正文或密钥。失败记录按游标继续处理其他任务，再按退避重试，防止一条坏数据阻塞整个队列。

历史任务由同一框架执行可恢复回填，使用主键游标、小批次和持久化进度。不要在应用启动迁移里扫描整张大表。已识别为非图片的记录不再反复读取，但以后写入图片结果时必须重新分类。

历史期限优先根据有效的 `finish_time`，其次根据保存响应中的有效完成/更新时间，再次使用有效 `updated_at`。候选时间必须在合理范围内，不能晚于当前时间或早于任务提交时间。无法确定完成时间的记录以首次识别时间建立 24 小时期限，并在回填报告单独统计，避免误删刚生成的结果。已过期的历史记录进入同一分批清理流程，不统一延长保留期。

回填尚未覆盖到的单条详情请求可以读取并识别该记录，执行相同的期限推导后再返回；列表不临时读取大 JSON，未知记录显示原状态，回填完成后统一准确展示。历史回填完成时间和剩余数作为启用验收指标。

## 列表与接口契约

在任务对象新增以下轻量字段；已有任务执行状态与响应外层结构保持兼容：

| 字段 | 约定 |
| --- | --- |
| `image_status` | `available`、`expired`、`partially_expired`；不适用或历史尚未识别时省略 |
| `image_expires_at` | 到期 Unix 秒 |
| `image_message` | 对应“图片已过期”或“部分图片已过期”；客户端用状态判断，不匹配中文字符串 |
| `image_has_url` | 供页面停留跨过到期时间时保留混合结果中的有效图片地址 |

管理员及用户的 `/api/task/`、`/api/task/self`、相应详情路径，以及 `/v1/tasks/:id` 等图片任务查询入口，都应用同一规则。任务存在且有权限时仍返回 HTTP 200。已存在的 provider/native 响应结构用对应序列化器扩展媒体状态，不能把所有协议强制换成同一种 envelope。

过期任务的图片任务接口示例：

```json
{
  "id": "task_example",
  "state": "succeeded",
  "progress": 100,
  "image_status": "expired",
  "image_expires_at": 1788746400,
  "image_message": "图片已过期",
  "data": {
    "images": [{ "image_expired": true }]
  }
}
```

示例省略了未改变的时间、usage 等字段；实现不能为了匹配示例而丢弃原有信息。过期标志必须在转换为精简 DTO 时保留，不能被只认识 `url/b64_json` 的旧图片结构丢掉。

到期后的返回内容中不包含受管理图片的 base64、data URI 或为该图片临时重新生成的 URL。已有普通 URL 不从数据库删除；不能声称本功能撤销用户已经下载的图片，或删除此前已独立存储在 R2 的文件。

读取入口先执行原有用户、令牌和工作空间鉴权，再检查过期。受管理图片返回 `Cache-Control: no-store`，序列化前再次检查当前时间，避免慢查询跨越到期边界后返回旧图。

默认及 classic 前端同步：过期时显示“图片已过期”，取消该图片的预览、下载和复制内容操作；详情保留任务信息。混合结果展示仍可用的图片和过期占位。前端根据服务器到期时间在页面停留期间自动更新状态，并释放已缓存图片引用；重新打开、页面回到前台和接口响应时重新校验。用户已下载的文件无法撤回。

## 发布与验收

实现入口为 `service/task_image_cleanup.go`；系统任务类型为 `task_image_base64_cleanup`，在系统任务页面显示“任务图片清理”。通过主节点环境变量 `TASK_IMAGE_BASE64_CLEANUP_ENABLED=true` 同时开启历史回填和物理清理，默认 `false`。代码中的到期读取限制独立于该开关。

每次运行的 `state/result` 记录扫描、更新、失败条数，移除字节数，历史时间估算条数，以及待回填数、待清理数、最老到期时间和续跑游标。正常期限固定为 24 小时，清理间隔固定为一分钟；单轮分配最多 500 条已到期记录和 500 条历史记录，执行预算 45 秒，额外积压统计查询限时 3 秒。

已有数据库通过 GORM 添加上述普通列和组合索引；未在启动迁移中加入历史大 JSON 扫描。SQLite 旧结构加列及原数据保留已有回归测试；MySQL/PostgreSQL 使用相同 GORM 更新路径，本次没有连接这些数据库执行迁移。

分阶段执行：先增加兼容列和索引，再发布期限写入、读取检查与两套前端，最后开启后台回填和清理。不能在一台新版本、一台旧版本混跑时开始清理，旧节点可能返回图片或回写旧内容。

生产 slave 跳过自动迁移，因此新列必须在发布需要这些列的备用节点前准备好。当前任务表约 17 GiB，增加列和索引可能产生锁等待或表重建；应单独验证迁移方式和数据库负载，不能把大表 DDL 隐藏进常规重启流程。清理开关关闭只暂停物理删除，已建立期限的读取限制和已清理标志仍生效。

| 验证项 | 必须满足 |
| --- | --- |
| 时间边界 | 24 小时前可读取，到期瞬间不可返回图片；尚未执行清理也成立 |
| 数据完整性 | 任务数量、执行状态、模型、usage、费用和所有关联记录保持一致 |
| 定向清理 | 多图、base64 别名、图片 data URI、混合 URL、失败请求残留正确处理；音视频和文本保留 |
| 并发与重试 | 重复清理幂等；旧快照写回被拒绝；到期不因查询而延后 |
| 上游隔离 | 过期查询不请求上游、不转存 R2、不触发结算或退款 |
| 权限 | 用户和工作空间隔离与当前接口一致 |
| 性能 | 列表仍省略大字段；按索引分批清理，记录积压及数据库压力 |
| 历史兼容 | 时间缺失、坏 JSON、断点续跑、部分失败不误删或阻塞队列 |
| 多节点 | 两台均执行过期读取规则，只有持有租约的主节点执行清理 |
| 前端 | 两套前端及各语言展示过期文案，跨到期时间的已打开预览也失效 |

清理减少的是活跃任务行中的图片载荷；任务记录和相关日志仍会正常增长。不能把“移除了多少 JSON 字节”当成磁盘文件立即缩小的证明，也不能承诺整个数据库只保留一天的数据。数据库物理文件回收和备份保留策略应单独评估。
