# 5000 并发素材压测结果（2026-10-10）

用户要求停止继续启动大型压测进程，本轮不再追加测试。本文只记录已返回的完整测试输出；排除客户端端口耗尽的单素材补测未取得最终结果，不计入结论。本轮没有修改业务代码。

## 参数与范围

- MySQL 5.7.43，独立合成数据测试库，本地上游固定延迟 20ms。
- 50,000 个背景素材，初始状态表 150,019 行；每场景再预置 5000 个素材。
- 两个应用进程，各主库连接池 30、日志库连接池 5。
- 5000 个并发创建，已有素材与创建成功的新素材每 3 秒轮询，共 11 轮。
- 单素材场景同时删除 5000 个素材；删组场景两个请求删除同一目标组，2500 个创建进入目标组、2500 个进入对照组。
- 客户端超时 90 秒。轮询允许重叠，没有把正在处理的请求数限制在 5000；单素材首轮采样峰值 56,443 个，删组场景 52,100 个。这给本机造成了过大负载，不能把结果解释为“固定最多 5000 个在途请求”的能力测试。

删组测试的归属断言通过，不表示性能通过：健康检查仍出现 18 次 503，延迟明显升高。

## 当前结论

1000 并发优化后的测试没有复现 503；提高到本轮 5000 创建并叠加持续轮询、删除后，两个场景均复现健康检查 503。已确认应用连接池被占满并排队；MySQL 服务端没有达到连接上限，也未观察到死锁或数据库锁等待超时。不能据此断言所有锁竞争都不存在。

全局素材查询的执行计划仍使用范围枚举及完整联合索引定位，没有证据表明这次退回了此前的全索引扫描。运行中的 SQL 包括重复渠道读取、素材读取、删除关联扫描和 COMMIT；仅凭采样不能把全部时间归因于某一种 SQL。

后续应先降低单请求的重复数据库访问和删除关联扫描成本，并明确轮询重叠策略。本轮未扩大连接池，未修改生产数据、历史记录或数据库结构。

## 停止压测后的静态复核

本次只重新阅读代码和已有记录，没有启动服务、编译、测试或压测。连接池被占满是观察到的现象，不足以单独证明哪条 SQL 是主要耗时来源；本轮请求累积到五万以上，也不能用于断言固定 5000 在途请求的容量上限。

### 1. 没有重试事件也会执行主库 UPDATE

`controller/configurable_resource_retry.go:79` 在资源请求完成后调用 `MarkRetryRouteFinal`。`service/retry_route_event_recorder.go:111` 只检查 request ID 是否为空，没有检查本请求是否实际登记过重试事件。`model/retry_route_event.go:145` 随即通过主库 `DB` 执行 `UPDATE retry_route_events WHERE request_id = ...`，即使没有匹配行也会借用连接并执行 SQL；当前 GORM 配置使用默认写事务。

因此“素材归属轮询不写入”仅描述归属表路径，不能扩大为“整个 GET 没有数据库写操作”。这与此前计数中的 UPDATE/COMMIT 开销相符，但没有逐条计时证据确认其贡献比例。

建议用请求内已成功创建重试事件的标记决定是否更新；没有事件时跳过数据库访问。需要保留 `relay_route_final_success` 上下文标记及真实重试事件的最终状态更新，不应为判断是否有事件再发一次数据库查询。

### 2. 同一请求重复读取渠道、账号范围，而且不响应查询取消

`controller/asset_access.go:348` 读取候选渠道，选中后 `:370` 又读取同一渠道。账号范围在 `:356` 查一次，随后 `prepareAssetAccess` 的 `:410` 再查一次。`model/channel.go:513` 的 `GetChannelById` 直接查询数据库；参数 `true` 表示读取完整字段，不代表使用缓存。

这两类模型查询使用全局 `DB`，没有传递请求 context。客户端取消后，已经进入这些路径的查询仍可能等待连接、继续执行。建议在同一请求中复用已验证的渠道与范围快照，并给读取路径传入 context；不能用跨请求旧缓存直接代替归属或凭据隔离检查。

### 3. 渠道查询错误可能被误报成 404

`controller/asset_access.go:348` 后对所有渠道读取错误直接 `continue`；最终没有匹配项时返回 `ErrAssetNotOwned`。因此数据库连接错误等基础设施异常也可能沿此路径返回本地 404。应区别“渠道记录不存在”和数据库异常，后者返回状态查询不可用。此项是代码确认的错误分支风险，不能据此把上一轮所有 404 判为错误。

### 4. 删除仍承担两次账号范围读取，并有不受请求取消控制的等待

`model/asset_binding_lifecycle.go:297` 的 `assetRevocationRecords` 按渠道、账号、用户和资源类型读取关联记录，在 Go 中按规范 ID、组 ID 筛选。单素材删除也使用该流程；不是每次只定位待删素材。

`model/asset_binding.go:553` 在事务外读取一次，`:582` 在取得身份锁后再读一次。解析缓存减少 JSON 解码，不减少数据库返回行数；发现新关联导致重试时还会重复读取。这会消耗连接、CPU、内存，并拉长已经持有身份锁的事务。

同一文件 `:548` 的删除槽位为每进程 4 个，等待使用普通 channel 发送，后续数据库操作也没有独立超时。大量客户端超时不代表这些删除收尾已经停止。不过调用位置在上游删除成功之后，不能简单取消全部本地收尾，否则会留下上游已删除、本地仍有效的归属。优化需要同时处理关联查找成本和收尾的可靠性，不能只移除锁或把槽位调大。

### 5. 已登记 GET 的读取次数仍较多

单个已登记 ID、一个有效渠道、关联不变、生命周期标记齐全的成功查询：归属定位两次读取、渠道两次、账号范围两次、响应后归属重读一次、生命周期读取一次；响应含组时通常再查一次组。按代码分支约为 8–9 次读取，另有上述重试事件 UPDATE，尚未计入鉴权或特殊供应商步骤。

这是静态路径计数，不是新增实测。应优先移除无效写入、重复渠道/范围读取，再在保留撤销与历史记录检查的前提下减少响应后的重复查库。

### 6. 三项健康检查共用期限会放大故障表象

`controller/misc.go:49` 中主库、日志库、Redis 串行共用 3 秒 context。主库借连接耗尽期限后，后续两项也会使用已过期 context，出现全部 unavailable；这不能证明日志库和 Redis 同时故障。独立、并行检查可以改善归因，但无法替代上述业务路径优化，也不应通过延长期限来掩盖排队。

建议顺序：无重试事件跳过 UPDATE；复用请求内渠道和范围并传递 context；正确区分数据库异常与不存在；随后单独处理删除关联扫描及可靠收尾。以上为复核发现和修改建议，本次没有改业务代码。
