# 素材资产并发优化待办（2026-11-20）

状态：按用户要求暂缓实施，仅记录问题、优化方向及验收要求。此次没有修改业务实现、数据库结构或持久连接池配置。

审查基线：本地 `9a3096198` 加当时未提交的适配修改；资产归属及事务期限逻辑已存在于 `1fd452a70`。背景见 [连接池风险修复](../reviews/asset_pool_remaining_review_20261011.md) 和 [素材关系按需补齐](../reviews/asset_relationship_repair.md)。

**已确认的问题集中在素材资产链路，不能据此断言其他接口绝不会受影响。** 共享 MySQL 连接池满载时，聊天、视频或后台请求可能间接受到排队影响；视频引用素材还会执行部分素材权限校验。这次没有对这些混合负载做验证。

| 接口 | 已有证据 | 结论边界 |
| --- | --- | --- |
| `POST /api/assets` | 1000 并发、主库池 30、Redis 关闭时，996 成功、4 次 `502 asset_binding_failed`；上游已接受创建，本地保存归属报 `context deadline exceeded` | 已复现高并发失败；原始失败轮没有逐请求阶段计时，不能断言每个失败都发生在借连接阶段 |
| `GET /api/assets/{id}` | 缓存命中后仍执行 9 条业务 SQL；1000 同步请求下主库池 100 会满载并排队，轮询均成功 | 已确认并发等待和查询成本，没有复现该接口超时失败 |
| 上传、列表、更新、删除、分组及各素材协议别名入口 | 共用部分资产归属或生命周期逻辑 | 没有在这轮相同负载下逐一验证，不能统称这些接口都失败 |

这里的素材处理 `task`/别名与视频生成任务不是同一个概念；这次结论不能扩展为所有图片生成、视频生成或模型转发接口都有同类故障。

实测基线：本地 MySQL 5.7.44、Redis 7.4.10、单实例、`GOMAXPROCS=4`、上游 mock 延迟 20ms。先同时创建 1000 个素材，再每隔 3 秒发起一轮查询，共 20 轮，各轮不重叠；这不是持续 1000 QPS。Redis 从冷缓存启动，TTL 保持 60 秒。

| 指标 | 主库池 100、Redis 池 10 | 主库池 100、Redis 池 100 |
| --- | ---: | ---: |
| 创建成功 | 1000/1000 | 1000/1000 |
| 轮询成功 | 20000/20000 | 20000/20000 |
| 创建 P95 | 3143.80ms | 2384.51ms |
| 轮询 P95 | 583.75ms | 522.95ms |
| 主库连接占用峰值 | 100/100 | 100/100 |
| 轮询阶段业务 SQL | 181000 | 180000 |

| 健康检查成功 | 124/124 | 122/122 |
| 结束时主库连接占用 | 0 | 0 |

两轮均通过状态转换、归属唯一性、普通轮询不改写归属及锁记录的校验；轮次延误、监控错误、Redis 池超时均为 0。每 100ms 采样未发现行锁等待，不能排除短暂锁等待。没有连接持续占用的迹象。

第一轮覆盖令牌缓存到期，轮询额外产生 1000 次令牌回源；第二轮轮询鉴权回源为 0。累计等待是并发请求相加的时间，不是墙钟时间。Redis 客户端耗时包括借连接、网络及调度，不能全部归为 Redis 服务端执行。扩大 Redis 池后数据库等待增加，表明仅看某一个连接池等待最少不能判断整体请求最快；两轮耗时还存在环境和缓存到期时点差异。

待实施的优化方向：

1. 梳理同一校验阶段的资产、父组及生命周期查询，合并可以合并的读取并复用已读结果。重点检查 `controller/asset_access.go`、`controller/asset_response_lookup.go`、`model/asset_binding_read.go`；不跨上游请求复用可能已经失效的授权结果，不新增跨请求所有权缓存。
2. 检查创建事务中 `resolveStored`、`assetRegistrationStates`、`saveAssetBinding` 的重复读取，在保持账号作用域、历史别名、冲突检测及锁顺序的前提下精简。不能因为使用了同一张表就直接删除查询。
3. 调整 `model/asset_operation.go` 的期限边界：借连接受整体 15 秒操作预算约束，取得连接后再开始较短的事务预算。目前 3 秒期限在获取连接前开始，排队会挤占事务执行时间。保留 MySQL 会话锁等待上限、连接参数恢复及失败后丢弃连接的保证，并兼容 SQLite/MySQL/PostgreSQL。
4. 对冷缓存及到期时的并发回源单独评估。避免为了资产压测直接改动全局鉴权语义，也不通过无条件重试上游创建、增加重复兜底或单纯扩大连接池掩盖问题。

后续验收要求：

- 复测用户隔离、账号切换、渠道停用、父组删除、并发撤销、历史别名修复、原始状态透传和普通轮询零写入。
- 用受控连接池耗尽测试证明：等待遵守整体期限，拿到连接后事务仍有正确的剩余预算，取消及失败不会泄漏连接、保留锁或部分登记。
- 完成 SQLite/MySQL/PostgreSQL 相关回归；若实际环境缺少某数据库，应明确未运行项，不能将跨库兼容推断写成实测通过。
- 同条件重跑 1000 并发创建及 20 轮查询，比较业务 SQL 数、借连接等待、连接持有时间、请求 P95、成功率和健康检查；保留冷缓存与到期行为，不只比较单个池的累计等待。
- 增加资产与普通请求混合负载验证，确认共享连接池是否拖慢其他接口。上述验收是待办，不代表本次已经完成。
