# 素材归属并发修改：独立审查与后续设计

日期：2026-10-08。审查对象：当前工作区的素材绑定、重试、批量撤销和相关测试。本文是审查结果和实现建议；没有修改业务代码，也没有部署。上一轮说明见 [死锁修复记录](asset_deadlock_review_20261008.md)。

后续更新：用户要求保持部署环境不变后，代码已撤去局部 RC，改用有序 ID 派生表驱动 MySQL 唯一主键查找，并以普通 INSERT 加整批回滚处理互斥初始化竞争。下面第 3 项记录的是已撤换的 RC 实现。2026-10-09，第 1、2 项也已完成[生命周期修复](asset_lifecycle_fix_20261009.md)，审查复现已转为正式回归测试。下文为当时审查快照，行号及测试结论保留原记录。

结论：已有死锁修复值得保留，但还不能作为“登记、别名补全、删除使用完整一致的并发协议”验收。固定锁顺序解决锁循环；完整生命周期约束还需要稳定身份锁和持久撤销状态。下面的生命周期问题原实现也存在，属于本轮尚未解决的缺口；MySQL STATEMENT 日志兼容限制来自新增的 READ COMMITTED。

## 已确认的问题

### 1. P1：删除使用加锁前的集合，漏掉已经成功提交的新别名

位置：`model/asset_binding.go:405` 读取集合；`:435` 加锁；`:438` 起直接更新原来的 IDs。

可控复现顺序：

1. 删除查询并得到只有旧句柄 A 的集合，暂停在查询完成处。
2. 查询响应登记 A、一个新素材别名 B 和一个新任务句柄 T，整个事务提交成功。
3. 恢复删除，删除按旧集合锁定并撤销 A，返回成功。
4. B、T 仍能通过 `FindAssetBindings` 查到有效归属。

SQLite、MySQL 5.7.43-log 均复现，删除单素材和删除分组两种情况均成立。测试模拟了控制器真实的“新增响应 ID + 原句柄”登记方式，并非只登记新别名的假设调用。

必须在取得协调锁后重新读取目标集合。若新集合需要额外的锁，回滚事务，在事务外准备缺失锁，再按完整顺序重试；不能持有一部分锁时任意补锁。

### 2. P1：删除结束后，迟到的登记仍可加入已撤销分组

位置：`model/asset_binding.go:326` 只为传入句柄准备锁，`:343` 只查询这些句柄的归属；没有检查 `GroupID` 指向的分组是否已经撤销。

HTTP 层已复现：

1. 创建素材请求通过分组授权，并到达上游；暂停上游响应。
2. 另一请求删除该分组，上游成功，本地分组归属变为无效。
3. 释放创建响应；当前接口返回 HTTP 200，并成功保存 `GroupID` 为已删除分组的素材。

模型层还复现了已有素材最初 `GroupID` 为空，在分组删除之后补全 `GroupID` 仍然成功。

这不是重新扫描删除集合就能解决的问题。登记必须在同一事务中检查素材身份与父分组的当前撤销状态；检查应覆盖创建、历史认领和查询补全。

另一个模型层边界也已复现：素材删除后，用相同 `CanonicalID` 和全新的 ID 调用 `SaveAssetBindings`，仍会成功。当前 get 控制器通常会附带旧句柄，因此不能把这个模型层复现直接宣称为普通 get 请求一定会复活素材；但它证明模型并没有提供“撤销整个身份”的约束。供应商本地 canonical ID 未必有自己的句柄行，不能只检查 canonical ID 对应的普通绑定来补这个缺口。

### 3. 条件性 P1：READ COMMITTED 与 MySQL STATEMENT 日志不兼容

位置：`model/asset_binding.go:188` 的事务隔离设置。

在隔离的 MySQL 5.7.43-log 中，将测试连接设为 `binlog_format=STATEMENT` 后，普通素材登记在初始化锁行时直接失败：

```text
Error 1665 (HY000): Cannot execute statement: impossible to write to binary log
since BINLOG_FORMAT = STATEMENT ... InnoDB is limited to row-logging when
transaction isolation level is READ COMMITTED or READ UNCOMMITTED.
```

上一轮文档已说明这一限制，本轮确认了实际报错。不能仅凭“MySQL 5.7.43 测试通过”推断目标部署满足条件。使用局部 RC 的方案需要 `log_bin=0` 或 ROW/MIXED；目标环境的真实日志配置本轮没有读取。若产品必须兼容启用 STATEMENT 的实例，则需要另外验证 RR 下的实现，不能捕获 1665 后直接切回 RR 并继续声称已有死锁保证成立。

### 4. 性能边界：SQL 次数减少不等于删除成本只随目标组增长

当前初始查询仍加载同一渠道、scope、用户的所有有效绑定，再逐行解析 Metadata 筛选目标。设该用户素材库有 N 条绑定、目标有 K 条，应用读取和解析仍是 O(N)，互斥及更新往返才是 O(K / 500)。删除很小的分组也会读取整个库。

本轮复测“1000 素材 + 1 分组”得到 10 条查询/修改 SQL，批量化效果成立。应同时记录扫描行数、响应字节和事务持锁时间，不能只用 SQL 条数验收大库中的小组删除。这个扫描问题也是原有结构的限制，并非本次修改引入的新退化。

## 建议保留的改动

- 互斥记录在业务事务外初始化；已有记录避免重复 UPSERT。
- MySQL 初始化采用 INSERT IGNORE；事务内先取得互斥，再做归属判断和写入。
- 锁记录按不可变主键排序，跨批次保持相同顺序。
- 撤销按 500 行分批，全部批次保持同一个事务，失败整体回滚。
- 已知冲突只重试完整本地事务，最多四次并退避；不重发已被上游接受的 HTTP 请求。
- 默认隔离级别不被素材事务改变；对 MySQL RC 的部署条件作明确约束。

## 建议的统一协议：稳定身份锁 + 撤销标记 + 锁后校验

继续复用 `ConfigurableResourceState`，不新增表、列或索引。将需要的状态存成独立命名空间的记录，不混用普通可访问素材绑定。

| 记录 | 身份范围 | 用途 |
|---|---|---|
| 现有句柄互斥 | 全局 kind + 句柄摘要，asset/task 合并 | 保留跨渠道归属冲突仲裁 |
| 素材生命周期记录 | ChannelID + Scope + asset/task 统一种类 + CanonicalID 摘要 | 所有别名共享的稳定身份、持久撤销状态 |
| 分组生命周期记录 | ChannelID + Scope + group + CanonicalID 摘要 | 协调删组、新建子素材和补全所属分组 |

稳定身份保留现有渠道和账号隔离语义；哈希应使用明确编码的元组，避免字符串拼接歧义。session 继续按凭据摘要和过期时间处理，不把 bearer credential 放入 Metadata 或生命周期键的明文部分。

所有登记、历史认领、补全和删除遵循同一流程：

1. **规划依赖。** 根据传入参数和已存元数据收集句柄、稳定素材身份、父分组。已存 `CanonicalID` 优先，不能把上游这次返回的新 ID 当作既有素材的新身份；未知分组补全要纳入新父分组。
2. **事务外初始化。** 仅创建缺失的中性协调记录，不取得一部分业务锁后再去初始化另一部分。
3. **统一排序加锁。** 将本次涉及的全部协调行合并，按主键升序锁定，包括跨批次顺序。禁止各条路径自行选择“先分组后别名”或“先别名后分组”。
4. **锁后重读与验证。** 重新读取权威元数据和删除集合。发现新别名、新子素材或变更后的身份依赖，且其锁不在计划中，则回滚、扩展计划、有限重试。不能边持锁边补齐任意顺序的锁。
5. **检查生命周期。** 登记必须同时检查有效素材身份与有效父分组；已撤销身份拒绝任何新句柄。只有“尚无已登记分组归属”的中性记录不能直接当成删除，需保留现有隐式上游分组的行为。
6. **原子提交。** 删除在同一事务中撤销目标生命周期记录及完整别名集合；删组也撤销已知子素材身份。这样后来即使只传新 ID、未附带旧句柄，也不能恢复已知被删素材。所有状态修改继续分批，并随事务一起提交或回滚。

这里的线性化点是本地归属事务提交。登记先提交，删除必须将其纳入；删除先提交，迟到登记必须被撤销状态拒绝。上游请求不放在持有数据库锁的事务里，这套协议也不等同于跨上游与本地数据库的分布式事务；上游成功、本地永久故障仍需保留现有明确的失败语义。

两个实现细节必须一并处理：

- 当前 SQLite 的加锁语句是 `UPDATE status='active'`。如果复用同一锁行承载撤销状态，这句会清除撤销标记！应改为不改变业务状态的写锁操作，或把中性互斥与生命周期状态分开存储。
- 历史已撤销绑定没有新生命周期记录。必须在受协调保护的初始化/回填中保留这些撤销状态，尤其是“canonical 没有独立句柄行”的情况；不能把所有新生命周期记录默认为有效后就认为兼容迁移完成。无需改表，但需要明确数据初始化策略。

这样无需把全站素材操作串行化。代价是同一分组中的写入会竞争分组协调锁；先以短事务保证正确性并测量吞吐。若实际成为瓶颈，再设计共享/独占锁分层，并重新证明全部加锁顺序，避免为了提前优化重新引入死锁。

针对 O(N) 扫描，如果实际库规模要求进一步优化，可在现有状态表中另存按 canonical/分组组织的关系记录，利用现有复合索引查询成员；这增加了双写、回填和一致性维护成本，应独立实现与验收。单纯把 UPDATE 分批不能消除扫描成本。
