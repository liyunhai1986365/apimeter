# 10 万素材、1000 并发 mock 压测（2026-10-26）

结论：**当前实现在本次配置下未通过该规模压测。已有素材详情查询正常，创建和列表出现大量本地超时。观测到连接池持续占满，未观测到数据库行锁等待；不能将失败归因于上游限流，也不能据此宣称没有任何短暂锁等待。**

完整数据：[JSON 报告](./assets_mock_100k_1000_20261026.json)。测试入口：`controller/asset_scale_test.go` 中的 `TestAssetLoad100K1000MySQL57`。

## 环境与方法

- 真正的 MySQL 5.7.43，随机独立数据库；主连接池 30、日志连接池 5，Redis 关闭。
- 单个测试容器运行网关、HTTP 压测客户端及 mock 上游，限制 4 CPU / 2 GiB，Go 内存目标 1400 MiB；MySQL 容器未设置 CPU / 内存配额。
- 使用当前 `ark-compatible` 素材接口和实际鉴权、归属校验、数据库逻辑。mock 每个请求延迟 1 ms，无配额或限流逻辑。
- 同一用户、同一渠道账户、同一组预置 **100,000 个素材**。先通过模型 API 创建原型，再批量生成同格式的 ownership / handle / lifecycle-v2 记录，初始约 **300,004 条状态记录**。校验素材总量及首、中、尾素材归属。
- 预置耗时 **20.01 秒**；正式请求阶段 **60.74 秒**；测试总耗时 **80.92 秒**。
- 详情、创建和列表分别同时释放 1000 个请求；这是并发突发测试，**不是持续 1000 QPS**。HTTP 客户端超时 20 秒。各阶段依次进行，超时请求的服务端善后可能延续至下一阶段。
- 数据库独立连接每 100 ms 采样，记录池占用、InnoDB 锁等待和持锁事务；GORM trace 记录所有主库 SQL 耗时及错误。

## 请求结果

| 阶段 | 成功 / 请求数 | 失败 | P50 | P95 | 最大耗时 |
| --- | ---: | --- | ---: | ---: | ---: |
| 已有素材详情，1000 并发 | 1000 / 1000 | 无 | 558 ms | 646 ms | 699 ms |
| 创建，1000 并发 | 22 / 1000 | 782 个 HTTP 502；196 个客户端未收到 HTTP 响应 | 15.37 s | 20.00 s | 20.00 s |
| 新建成功素材查询，3 轮 | 66 / 66 | 无 | 82 ms | 4.60 s | 4.61 s |
| 单次列表，第一页 20 条 | 1 / 1 | 无 | 14.04 s | 14.04 s | 14.04 s |
| 列表，1000 并发 | 0 / 1000 | 978 个 HTTP 500；22 个客户端未收到 HTTP 响应 | 15.97 s | 18.53 s | 20.02 s |

客户端无 HTTP 响应记录在 JSON 的 `http["0"]`，不是 HTTP 状态码 0；这些请求触及本轮 20 秒客户端超时窗口。耗时分位数包括成功和失败请求。

新建素材查询只有 **22 并发**，因为仅 22 次创建返回成功；不能将其称为 3000 次查询或 1000 并发查询。真正的 1000 并发详情验证来自已有素材阶段。

mock 实际收到 997 次创建请求，均走成功响应分支。网关创建失败响应为 `asset_binding_failed`：上游已接受，但本地归属保存失败。日志记录大量 `persist asset access binding: context deadline exceeded`。部分客户端超时后，独立的绑定善后仍可能完成；没有另行记录最终成功持久化总数，22 仅表示客户端收到的成功应答。

列表错误为 `asset_state_unavailable`，日志为 `list asset bindings: context deadline exceeded` 或客户端取消。后台 readiness 探测 **58 次 200、7 次 503**，失败依赖为主数据库；status 探测 **21 / 21 成功**。因此本地数据库压力已经影响健康检查。

| 创建阶段连续满池采样跨度 | 21.10 s |
| 跨创建及后续查询阶段的最长连续满池采样跨度 | 25.70 s |
| 1000 并发列表阶段连续满池采样跨度 | 18.81 s |
| 结束时主池使用连接数 | 0 / 30 |
| 监控查询错误 | 0 |
| 测试容器 OOM | 无 |

“连续满池采样跨度”使用相邻连续满池记录的实际时间戳计算；高负载下 ticker 可能丢 tick，不能简单将采样数量乘 100 ms 当成精确持续时间。采样无法排除两次记录之间的短暂变化。

MySQL 5.7 的 `trx_started` 只有秒精度，810.82 ms 是被采样到的持锁事务年龄上界，**不是精确的锁持有时间**。加锁 SQL 的耗时也不等于整个事务的持锁时间。

共记录 48,405 次 SQL，最大 GORM trace 耗时 19.23 秒；1,578 次 `deadline_exceeded`、133 次其他错误。trace 包括等待连接池的时间，不能把这 19.23 秒直接解释成数据库执行某条 SQL 的时间。连接池累计等待 45,745 次，累计等待时长约 31,431 秒，是多个 goroutine 等待时间相加，不是本次测试墙钟时长。

## 定位与边界

本轮直接确认的问题是**本地归属处理超时、连接池持续饱和和列表无法承受目标并发**。未出现可观测的长时间行锁等待或死锁；测试结束时连接已释放。

代码中有两个需要优先分析的规模相关路径：

1. `model/asset_binding_identity.go` 的 `loadAssetBindingHistory`：新素材缺少身份记录时，通过 `metadata LIKE` 发现历史关联；源码明确说明没有 canonical-ID 索引，会检查账户范围内的历史记录。此过程发生在写事务之外，会增加查询及连接池压力，但不等于长时间持有行锁。
2. `controller/asset_list.go` 的 `newAssetListPagination` / `filterAssetListResponse`：先遍历当前用户的素材归属，再扫描上游分页进行过滤和总数计算。即使客户端只要第一页 20 条，也可能处理整个素材集合；本轮单请求约 14 秒，1000 并发时本地归属遍历超时。

本轮未按 SQL 类型分摊耗时，以上是结合日志和代码识别的优化方向，不能给出各路径的精确耗时占比。不要仅增加连接池或放宽超时就认定问题解决。

本次只测试创建、详情、列表；没有重跑此前全部 10 个接口。库存为当前 lifecycle-v2 格式，不覆盖所有旧格式迁移、多租户分布和真实上游网络情况。

## 复现与清理

准备仅用于测试、允许创建和删除随机 schema 的 MySQL 5.7 DSN，通过环境变量传入，避免提交凭证：

```sh
ASSET_LOAD_100K_1000=1 ASSET_LOAD_REPORT_PATH=/tmp/asset-scale-report.json \
  go test ./controller -run '^TestAssetLoad100K1000MySQL57$' -count=1 -v -timeout=8m
```

还需设置 `ASSET_TEST_MYSQL_DSN`。测试有失败请求时会返回失败，报告在断言前写出。默认未显式启用时跳过此大规模测试。

首次预检的创建请求误带 `ProjectName`，被渠道契约以 400 拒绝；修正请求后完整重跑。上面的正式结果仅取修正后的完整运行。

两轮共 4 个随机测试 schema 已清理并复核残留为 **0**；2 个停止的压测容器已删除，私有 DSN 文件已删除。未访问 MoreRouter 或真实上游。新增内容仅为压测夹具和报告，本次没有修改业务实现。
