## 初始混合压测

环境：MySQL 5.7.43，两个本地进程，每个主库连接池 30；独立日志库和 Redis；本地上游。每阶段预置 1000 个素材，新增 1000 个并发创建，已有素材及创建成功的素材每 3 秒轮询，持续 11 轮。单素材阶段同时删除 1000 个素材；组删除阶段两个实例同时删除目标组，新创建一半进入目标组、一半进入对照组。

| 指标 | 单素材删除阶段 | 组删除阶段 |
| --- | ---: | ---: |
| 业务请求数 | 24,000 | 20,615 |
| 健康检查 | 638 次，全部 200 | 627 次，全部 200 |
| HTTP 503 | 0 | 0 |
| 死锁 / 数据库锁等待超时 | 0 / 0 | 0 / 0 |
| 删除请求最大总耗时 | 12.882 秒 | 7.405 秒 |
| 删除取得锁后处理最大耗时（不含 COMMIT） | 98.854 毫秒 | 379.108 毫秒 |

单素材阶段 1000 个新素材创建和 1000 次删除全部成功；组删除阶段对照组 500 次创建、5500 次查询全部成功。目标组删除后拒绝的创建/查询返回 404，已删除关联未被迟到请求恢复。这里的上游错误由本地测试服务产生，不能作为字节官方错误码的证据。

本轮只说明该规模下未复现 503。旧索引缺少全局句柄查找所需的前缀条件，全局查询仍可能扫描覆盖索引；删除仍需在持锁后扫描当前账号的关联以发现并发提交的别名和子素材。批量删除存在排队，创建与同组删除仍有必要的锁竞争。没有宣称所有扫描、超时或 503 已消除。

原始日志、测试运行脚本和 JSON 指标：`/tmp/apimeter-asset-adjust-20261010/`。初始混合压测报告：`pool-30/report.json`。

## 扩大存量：1 万素材

额外预置 10,000 个同用户、同账号、其他组的合成素材，对应初始 30,019 行资源状态记录；随后各阶段再预置 1000 个素材，发起 1000 个并发创建和每 3 秒一次的轮询。此处扩大的是数据库存量，并发规模仍为 1000。

| 指标 | 单素材删除阶段 | 组删除阶段 |
| --- | ---: | ---: |
| 业务请求数 | 24,000 | 18,118 |
| 健康检查 200 / 503 | 471 / 19 | 663 / 1 |
| 业务 HTTP 503 | 0 | 0 |
| 死锁 / 数据库锁等待超时 | 0 / 0 | 0 / 0 |
| 采样到的锁等待事务峰值 | 0 | 10 |
| 两实例主库连接使用峰值 | 各 30/30 | 各 30/30 |
| 单次连接池等待平均值（两个实例） | 1623 / 1624 毫秒 | 354 / 938 毫秒 |
| 删除取得锁后处理最大耗时（不含 COMMIT） | 507.642 毫秒 | 657.418 毫秒 |

单素材阶段 1000 次创建全部成功，整批完成约 33.35 秒；1000 次删除全部成功，但最长请求约 73.77 秒。健康检查 503 响应约 3 秒，并再次出现主库、日志库、Redis 同时报 `unavailable`。三项检查串行共用同一个 3 秒 context，主库连接排队耗尽期限后，后续两项也会失败，不能据此认定三个依赖同时故障。

该阶段 MySQL 总连接峰值为 79，`Connection_errors_max_connections=0`；即使没有采样到锁等待事务，应用连接池仍满并发生健康检查超时。当前优化没有彻底解决大存量下的 503，剩余全局句柄扫描与删除关联扫描仍需重点处理。

原始报告：`/tmp/apimeter-asset-adjust-20261010/background-10000-pool-30/report.json`；精简指标：同目录 `summary.json`。

## 扩大存量：5 万素材，单素材删除

额外预置 50,000 个素材，初始资源状态记录 150,019 行。仍为两个进程、每池 30 连接、1000 并发创建、3 秒轮询、同时删除 1000 个素材。

- 健康检查 140 次：200 为 3 次，503 为 137 次。
- 业务请求 13,418 次：200 为 1307 次，404 为 2984 次，500 为 232 次，502 为 175 次，客户端 90 秒超时为 8720 次。报告中的状态 `0` 表示客户端未收到 HTTP 响应，不是服务器返回的状态码。
- 1000 次创建只收到 38 个成功响应，962 次客户端超时；1000 次删除只收到 6 个成功响应，994 次客户端超时。创建成功响应后才启动新素材轮询，因此本轮总请求数低于正常的 24,000 次。
- 两个应用连接池均达到 30/30；单次连接池等待平均约 11.31 秒、10.25 秒。MySQL 总连接峰值仍为 79，连接上限错误数为 0。
- 未观察到死锁、数据库锁等待超时或锁等待事务；单次删除取得锁后的处理最长约 1.81 秒（不含提交）。
- 查询执行计划：全局素材 ID 查找为 `type=index`，使用 `idx_configurable_resource_state_scope`，估计扫描 132,547 行，`Using where; Using index`。这表示覆盖索引扫描，不是按素材 ID 精确定位。
- 运行中 SQL 采样曾同时记录 60 个连接执行该全局素材 ID 查询，覆盖了两个实例全部主库连接。

500 的本地错误码为 `asset_state_unavailable`；502 为 `asset_binding_failed`。本轮上游仍为本地响应服务，不能归因为字节上游返回这些错误。

本轮未通过。结束采样时 991 个待删除素材仍有有效本地登记；由于 994 个删除请求已经在客户端超时，这不能解释为“成功删除后被复活”。原混合脚本的“全部已删除”断言因此失败，组删除场景改用另一个新建测试库单独执行，避免继续叠加未完成请求。

原始报告：`/tmp/apimeter-asset-adjust-20261010/background-50000-pool-30/report.json`；精简指标：同目录 `summary.json`。

## 扩大存量：5 万素材，独立组删除

重新创建独立测试库，预置相同的 50,000 个素材和 1000 个待删除组内素材。只有两个删除组请求；1000 个新建请求一半进入待删组、一半进入对照组；轮询仍为每 3 秒一次、11 轮。

- 健康检查 208 次：200 为 140 次，503 为 68 次。
- 业务请求 17,458 次：200 为 5927 次，404 为 11,503 次，客户端 90 秒超时为 28 次。
- 对照组 500 次创建中，473 次收到成功响应、27 次客户端超时；结束校验时 500 个登记都已完成。超时不代表创建没有发生。
- 两次组删除均返回 200，耗时约 70.28 秒和 85.06 秒；已删组没有残留有效子素材登记，对照组 500 个素材仍有效。
- 轮询超时 1 次；对照组 5203 次轮询全部 200，但 P95 已达约 45.13 秒。
- 两个应用连接池均达到 30/30，单次连接池等待平均约 5.32 秒、5.50 秒；MySQL 连接峰值为 79，无连接上限错误。
- 未观察到死锁或数据库锁等待超时；采样锁等待事务峰值为 1。删除取得锁后处理最大约 1.14 秒（不含提交）。

该脚本的归属一致性断言通过，但性能没有通过：健康检查仍大量 503，创建和查询仍存在客户端超时。独立场景也说明，问题不只由大量单素材删除请求积压引起。

原始报告：`/tmp/apimeter-asset-adjust-20261010/background-50000-group-pool-30/report.json`；精简指标：同目录 `summary.json`。
