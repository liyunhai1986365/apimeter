# 100 用户、10 万素材、1000 并发：列表修复复测

修复后 10 个接口每项 1000 次请求全部成功，素材列表 P95 5.67 秒、最大 5.68 秒。没有新增索引、修改表结构、增加连接数或延长超时。

## 修复方式

1. 同一渠道、账户、资源类型的并发归属读取按批合并。SQL 只按现有复合索引枚举账户，再按 `state_value` 中的真实所有者分发；不再对每个用户重复做带所有者条件的元组发现及账户扫描。后到的请求进入下一次新扫描，已完成结果不缓存。保留旧 `user_id/token_id` 存储元组兼容。
2. 相同账户、认证、筛选条件的上游分页在列表扫描期间复用，并共享一次解析结果。用户独立计算自己的列表、总数与游标，查齐后独立结束。分页保留具有全局 64 MiB 载荷预算，超出预算时退回普通并发合并；最后一个扫描退出后释放。单组超过原有 1 分钟扫描期限不再接受新扫描，避免持续流量无限续期。该预算不是整个进程内存上限。
3. 用户归属和撤销结果不缓存。每个读取者检查当前身份及父组关系，实际返回页再次按调用者核对所有者、规范 ID 和撤销状态。首次缺失关系仍走已有兼容补齐流程。

此次没有改变已有渠道配置，未调用真实供应商。

## 相同压测条件

- 100 用户共同拥有 100,000 条历史素材，每人 20–1,980 条，不均匀分配；共享一个上游账户。
- 每用户每波 10 个请求，总并发 1000；各波实际峰值均为 1000。创建后列表阶段共 101,000 条素材。
- MySQL 5.7.43-log；主池 30、日志池 5；容器 4 CPU / 2 GiB；本地 mock 延迟 1 ms；客户端超时 20 秒。
- 真实 HTTP Action 路由、Token 鉴权、素材归属/撤销检查。没有为创建重试来掩盖请求失败。
- 初始历史关系完整；另删每用户一个关系，测试按需补齐及补齐后的查询。

满池跨度来自约 100 ms 采样，不是逐连接持有时间。修复后最长连续满池为 10 个采样点，首尾跨度 1.147 秒；仍有短时排队，但未导致错误。列表 SQL 最大耗时 993.64 ms（含排队），没有加锁 SQL、metadata LIKE 或 SQL 错误。

列表阶段实际执行 2 次账户元组发现、406 页归属读取，总共读取 202,000 条归属，即两个冻结批次各读 101,000 条；没有为 100 个用户各做一次全账户遍历。上游 2009 次由每个请求原有的第一页共 1000 次，加后续共享的 1009 页组成。

原始最终 JSON 的 `list_owner_scope_discovery` 分类包含 1000 次 `asset_candidates` 派生表精确归属复核，不是原来的全账户用户筛选查询；可由每类保存的 SQL 样例核对。测试源码已将它单列为 `ownership_recheck`，没有改写已采集的原始结果。

中间验证 `multiuser-fixed` 仅完成数据库合并和同时进行的单页请求合并，健康检查全部恢复，但列表仍 990 次客户端超时。它证明只修数据库不足以解决用户进度错开造成的上游重复读取；最终版本补齐了扫描期间的分页复用。中间失败记录也保留。
