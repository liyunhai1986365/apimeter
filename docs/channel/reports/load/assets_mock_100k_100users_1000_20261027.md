# 100 用户、10 万历史素材、1000 并发测试与列表诊断

本轮创建、详情查询等 9 个接口均为 1000/1000 成功；素材列表失败。失败集中在按用户加载素材归属时的重复扫描与连接池排队。关系补齐后的详情查询通过；列表失败阶段没有加锁 SQL，也没有采样到行锁等待。

## 场景

- 100 个平台用户共 100,000 个历史素材，不均匀分配，每人 20–1,980 个；每人另有一个素材组。
- 100 个用户共享同一渠道/上游账户，每用户每波 10 个请求，总并发 1000。所有正式波次实际在途峰值均为 1000。
- 使用 `ark-compatible`，经过真实 HTTP Action 路由、Token 鉴权及用户归属校验。上游为本地 mock，固定延迟 1 ms，不调用真实供应商。
- MySQL 5.7.43-log；主库池 30、日志库池 5；Redis 及鉴权内存缓存关闭。网关、压测客户端和 mock 同处 4 CPU / 2 GiB 测试容器，MySQL 在独立容器；没有 OOM。
- 初始关系是完整的 v2 数据。另单独删除每用户一个素材身份关系，验证缺失关系的兼容补齐，不能把本次称为“10 万条关系都缺失”。
- 每波结束等待网关和 mock 在途请求归零再开始下一波；客户端超时 20 秒。没有改索引、表结构或业务代码。

## 为什么列表失败

`WalkAssetBindingsContext` 按 `state_value = 用户 ID` 加载这个用户的完整素材归属，再按上游结果筛选、分页。实际素材所有者存放在 `state_value`，现有复合索引中的 `user_id` / `token_id` 是用于唯一归属约束的存储元组，新记录均为 0。因此索引能定位到账户范围，但不能直接定位到实际素材所有者。

`walkScopedAssetStateRows` 有两个成本：

1. 发现已有存储元组的 `GROUP BY` 查询继承了用户和状态筛选，需要扫描账户素材范围，不能使用索引的分组跳读。
2. 分批加载该用户素材时仍需从账户索引范围按 `state_value` 过滤；每页只返回最多 500 个归属记录，不代表只读取 500 条索引记录。

100 个用户的最终列表结果不同，现有并发合并按用户隔离，无法合成一个列表结果。每个用户都重复发现元组、过滤账户范围，挤满 30 个连接；之后连 Token 鉴权和账户范围的精确查询也会排队。

第一轮列表阶段：

- 连续 154 个满池采样点，首尾跨度 15.332 秒，采样间隔约 100 ms；这是采样跨度，不是逐连接精确计时。
- 51 个 SQL 截止时间错误，日志明确出现 `list asset bindings: context deadline exceeded`，对应本地归属操作的 15 秒上限。
- 列表阶段加锁 SQL 为 0、采样锁等待为 0；最大 SQL 耗时 13.39 秒，包含连接池等待。
- 客户端 402 个请求达到 20 秒超时（报告中的 HTTP `0` 表示没有收到响应，不是实际 HTTP 状态码）。
- 健康检查 47 次中 2 次返回 503，均为数据库探针 3 秒超时。
- 1000 个列表请求发出 33,264 次 mock 上游分页请求。即使本地归属读完，上游逐页枚举也仍有成本。
- 波次结束约 25.6 ms 后在途请求清空；测试结束主池占用为 0，没有残留挂住的请求。

## SQL 实测与第二轮复现

第二轮重建同样的数据分布，在创建 1000 个新素材后，账户共有 101,000 个素材。用独立固定连接读取 `SHOW SESSION STATUS` 前后差值，不重置全局计数器；`Handler_read_next` 是该连接顺序读取索引记录的次数，区别于 EXPLAIN 的估算行数。

用户 1 只有 20 个历史素材，加上新建后共 30 个：

| 查询 | 返回行数 | Handler_read_next | 耗时 |
| --- | ---: | ---: | ---: |
| 原有存储元组发现查询 | 1 | 101,000 | 431.62 ms |
| 原有素材归属第一页查询 | 30 | 101,000 | 416.58 ms |
| 元组发现去掉用户/状态筛选，仅作诊断对比 | 1 | 0（3 次键定位） | 0.44 ms |

用户 50 和 100 的元组发现也各顺序读取 101,000 条；第一页分别读取 47,945 和 26,100 条才返回 500 行。元组发现对比 SQL 的 EXPLAIN 出现 `Using index for group-by`，而原查询为 `Using index condition; Using where`，并带临时表和排序。

这只是诊断 SQL 对比，没有修改业务查询，也没有证明单改这一处就能解决整个列表问题。后续素材归属扫描、上游枚举仍然存在。

第二轮列表为 56 成功、280 个 502、664 个客户端超时；其余 9 个接口仍全部成功。分类追踪记录：元组发现查询最大 13.63 秒，归属分页最大 10.63 秒，关系精确查询最大 8.45 秒；这些均包含连接池等待。连 Token 等其他查询也达到 11.60 秒，说明慢扫描占用共享连接后把等待扩散到正常请求。该轮列表仍为 0 加锁 SQL、0 采样锁等待，健康检查出现 3 个 503。两轮的失败比例会随调度变化，但瓶颈一致。

## 不加索引、不改结构的后续方向

1. 发现存储元组时只按渠道、账户、资源种类定位，归属和状态仍在取素材及最终返回前校验，去掉这一次重复全范围扫描。
2. 合并同一账户上重叠的归属枚举，读取一次后按所有者分发；不能直接跨用户复用已经筛选好的列表响应。
3. 对相同账户、认证、筛选条件的上游分页考虑合并读取，保留各用户独立筛选及返回页的实时归属/撤销复核。

不建议只增加连接数或延长超时；这样不会消除重复扫描。
