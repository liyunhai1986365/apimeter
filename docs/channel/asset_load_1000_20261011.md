# 1000 个素材创建及每 3 秒并发轮询（2026-10-11）

本次未复现 503：1000 次创建、20000 次素材查询、121 次就绪检查、20 次服务状态查询全部返回 HTTP 200，测试通过。压测容器内存峰值约 283 MiB，未触发 OOM。

## 范围与资源限制

- 使用当前工作区代码的真实 HTTP 路由、Token 鉴权、素材控制器和数据库归属操作；单实例。
- 复用 MySQL 5.7.43-log，建立随机隔离主库及日志库，测试结束自动删除；不修改业务数据和数据库全局参数。
- 主库连接池 30，日志库连接池 5，开启 GORM 预编译语句。Redis 和鉴权内存缓存关闭。
- 项目 nmyk，同一个预登记素材组，1000 个创建请求同时释放。创建全部完成后，每轮同步释放 1000 个查询，共 20 轮，轮次起点间隔 3 秒。
- 单个客户端最多一个在途请求，轮次不重叠、不堆积；客户端连接上限 1016，创建及查询实际在途峰值均为 1000。使用 goroutine，没有启动 1000 个系统进程。
- 本地上游每次延迟 20 ms；前 3 次查询返回 Processing，之后返回 Active。该状态变化用于验证透传，不代表官方处理速度。
- `/api/ready` 每 500 ms 检查一次（另有启动探针），`/api/status` 每 3 秒查询一次。
- 独立压测容器硬限制 1 GiB 内存，不允许额外 swap，CPU 上限 2 核，PID 上限 256；`GOMAXPROCS=2`、`GOMEMLIMIT=640MiB`。此硬限制覆盖客户端、本地上游及网关测试进程，现有 MySQL 容器不在该限制内。

## 结果

| 操作 | 请求数 | HTTP 200 | HTTP 503 | P95 | 最大耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 素材创建 | 1000 | 1000 | 0 | 1894.302 ms | 1983.361 ms |
| 素材查询 | 20000 | 20000 | 0 | 836.931 ms | 903.316 ms |
| `/api/ready` | 121 | 121 | 0 | 171.747 ms | 301.621 ms |
| `/api/status` | 20 | 20 | 0 | 1.019 ms | 1.843 ms |

创建阶段约 1.996 秒，整个负载阶段 59.845 秒。迟到轮次 0，客户端错误 0；Processing 3000 次，Active 17000 次。全部 1000 个 ID 的归属均存在且唯一，轮询前后归属及锁标记行完整快照一致，没有被状态轮询改写。

主库连接使用峰值 30/30，借连接等待 233989 次，累计等待 14153.073 秒，平均每次等待约 60.49 ms。这是所有并发 SQL 的等待总和，不是单个请求等待了这么久。每 5 轮输出的轮末 InUse 均为 0，未观察到持续占满。日志池使用峰值 1/5，借连接等待 0 次。

每 100 ms 使用独立连接采样测试主库的 InnoDB 锁等待事务，观测峰值 0，监测错误 0。不能排除短于采样间隔的瞬时锁等待。

容器 cgroup `memory.peak` 为 296796160 字节（约 283.05 MiB），`memory.events` 中 `max`、`oom`、`oom_kill` 均为 0，Docker `OOMKilled=false`，退出码 0。运行中一次采样显示现有 MySQL 内存约 721 MiB（运行前约 696 MiB），此值不是 MySQL 全程峰值。负载结束后测试容器与临时凭据文件已清理。

## 复现与结论边界

入口为 `controller/asset_load_mysql57_test.go` 的 `TestAssetLoad1000CreateAndPollMySQL57`；显式设置 `ASSET_LOAD_1000=1`、`ASSET_TEST_MYSQL_DSN` 后才运行，并强制检查 MySQL 5.7 版本。`ASSET_LOAD_REPORT_PATH` 可保存统计 JSON。容器限制由运行器设置，不是测试函数自身设置。

结构化结果见 `asset_load_1000_20261011.json`；本次日志保存在 `/tmp/asset-load1000-20261011/test.log`，运行器在 `/tmp/run_asset_load1000.py`。

相较 100 并发，连接池等待和接口延迟明显增加，但本次 1000 并发仍在 3 秒轮询周期内完成，健康检查没有超时。本次不能证明双实例、海量历史记录、创建与轮询持续混合、真实慢上游或 Redis 故障下不会产生 503。只扩展了测试与报告，没有修改业务代码。
