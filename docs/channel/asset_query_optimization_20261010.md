# 素材查询扫描优化（2026-10-10）

本轮针对大存量下的全局句柄扫描和重复组查询，延续 [锁调整及优化前压测记录](asset_lock_adjustment_20261010.md) 中的约束：不改变表结构或索引，不迁移、回填、批量修改历史数据，不限制创建或查询并发。只在独立 MySQL 5.7 测试库中生成压测数据，上游使用本地响应服务。

## 代码变化

1. `model/asset_binding_read.go`：MySQL 全局查找先按现有联合索引前六列枚举不同范围，再使用完整七列等值查找候选主键。范围包含渠道、profile、资源类型、账号、user_id、token_id；保留所有账号和旧范围，不缓存授权结果。SQLite/PostgreSQL 保留原有可移植查询。
2. 批量别名以参数化派生表参与等值连接。MySQL 5.7 对范围连接后追加 `state_key IN (...)` 只利用前六列，仍会扫描账号内素材，因此没有采用这种写法。
3. 候选主键只用于定位，随后仍实时读取归属和有效状态。首次认领、跨账号冲突和路由歧义校验仍然执行；此次查询优化没有增加行锁。
4. `controller/asset_access.go`：响应中的组归一化已知渠道和账号，直接使用完整范围查询，不再全局搜索同名组。同一响应重复出现的 GroupId 只查一次；本请求已验证且项目非空的同一组可复用。项目尚未补齐的组仍重新读取，保留项目冲突检查和原始 ID 到规范 ID 的转换。

没有删除现有删除并发保护。删除后的状态仍由写事务复核，查询不能重新激活已撤销素材。

## 执行计划和回归

- MySQL 5.7.43，15 万状态行的独立 SQL 探测：旧查找约 42.8ms；两个句柄的完整索引查找约 0.76ms。这是单条 SQL 的十次平均值，不是接口并发延迟。
- 大存量复测执行计划：范围枚举为 `Using index for group-by`，估算 32 个范围；素材候选查找为 `type=ref`、`key_len=2087`，七列全部参与，估算每范围 1 行。派生范围表的 `ALL` 只遍历范围结果，不表示扫描全部素材。
- MySQL 素材回归通过：model 12.252s，controller 25.037s。新增执行计划测试检查单句柄和多句柄都使用完整索引；归属测试覆盖新账号即时可见、不同所有者、旧范围、撤销、任务句柄回退、发现主键后发生删除等情况。
- SQLite 功能兼容回归通过：model 2.343s、controller 7.040s、router 0.120s；没有进行 SQLite 压测或 PostgreSQL 实测。
- 响应测试覆盖重复组只查一次、已验证组复用、账号隔离、项目冲突、空项目重新读取、多个组字段相互冲突。

## 5 万素材复测

每个场景重新创建测试库，额外预置 50,000 个背景素材，初始状态表 150,019 行。两个进程，各主库连接池 30、日志库连接池 5；本地上游固定延迟 20ms。每阶段再预置 1000 个素材，发起 1000 个并发创建，已有素材和创建成功的新素材每 3 秒轮询一次、共 11 轮，轮次允许重叠。单素材场景同时删除 1000 个旧素材；删组场景两个请求同时删除目标组，500 个创建进入目标组，500 个进入对照组。

两轮共 45,044 个业务请求、2236 次健康检查，未复现 503。该结论仅适用于本轮 MySQL 5.7、本地上游和压力组合；单素材批量删除仍有 242 次超时，不能宣称全部性能问题解决。范围枚举成本随账号范围数量增长，删除仍扫描当前账号的关联记录；这两点不因单素材查找使用完整索引而消失。
