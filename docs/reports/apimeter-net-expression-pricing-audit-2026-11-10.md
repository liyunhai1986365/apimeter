# api.apimeter.net 线上表达式定价兼容性清单

日期：2026-11-10。数据来源：只读访问 `https://api.apimeter.net/api/pricing`。公开接口返回 113 个模型，其中 30 个使用表达式定价，对应 26 条不同公式。线上 `/api/status` 返回版本 `v1.0.24-43c4044e8`，与本地分析基线一致；首页初始 JS 文件名也与本地产物一致。

本报告将线上公开公式交给本地当前版本的前端解析器和后端执行器验证，没有登录管理后台、修改配置或发起计费请求。公开接口可能不包含停用模型、其他权限或分组下的模型；结论仅覆盖本次返回的 113 个模型。

## 1. 直接结论

- **6 个模型无法还原成可视化编辑配置**，分别是 5 个 DeepSeek 模型和 1 个 Seedream 模型，见下一节。
- **24 个模型能够还原成可视化配置**。其中 20 个生成公式与原文相同，4 个会改写形式；本次未发现这 4 个的系数、命中档位或计算结果变化。
- 30 个模型都能被价格展示解析器找到至少一个档位，不能把“无法可视化编辑”理解为价格页面一定整块不显示。
- **16 个模型的请求、时间或 `img` 条件未被价格展示解析器还原**。其中一个模型的整体 `0.5` 折扣倍率也没有被提取。价格能显示，不代表条件和倍率已经完整展示。
- 26 条不同的原式均通过当前后端编译和样例执行；没有发现本次公开公式属于“前端接受、后端无法编译”的情况。

## 2. 无法可视化编辑的 6 个模型

| 模型 | 线上公式的关键结构 | 不支持的原因 | 价格展示的影响 |
| --- | --- | --- | --- |
| `deepseek-v4-1-flash-260910` | `tier("base", ...) * (复合时间条件 ? 0.5 : 1)` | 时间条件包含多组 `||`、嵌套 `&&` 和换行，倍率拆分器无法还原 | 能显示基础单价，但 `0.5` 倍率及适用时段没有被提取 |
| `deepseek-v4-flash` | `(上午时段 || 下午时段) ? tier("peak", ...) : tier("off_peak", ...)` | 可视化档位条件不支持这种通用 OR 组合 | 显示峰值、非峰值两档价格，但没有完整时间条件 |
| `deepseek-v4-flash-0731` | 与 `deepseek-v4-flash` 相同 | 同上 | 同上 |
| `deepseek-v4-pro` | `(上午时段 || 下午时段) ? tier("peak", ...) : tier("off_peak", ...)` | 可视化档位条件不支持这种通用 OR 组合 | 显示两档价格，但没有完整时间条件 |
| `deepseek-v4-pro-0813` | 与 `deepseek-v4-pro` 相同 | 同上 | 同上 |
| `doubao-seedream-5-0-pro-260628` | `img <= 2360000 ? tier("image_normal",43000) : tier("image_hd",86000)` | token 条件只支持 `p`、`c`、`len`，不接受 `img` | 显示两档固定费用，但不能展示这个阈值条件 |

DeepSeek 的 OR 条件原文是：

```text
((hour("Asia/Shanghai") >= 9 && hour("Asia/Shanghai") < 12)
 || (hour("Asia/Shanghai") >= 14 && hour("Asia/Shanghai") < 18))
```

后端能执行这段条件。当前可视化解析器支持部分时间比较以及特定的跨午夜范围形式，但没有任意布尔条件树的表达能力，因此无法将上述 OR 组合还原为表单。

`deepseek-v4-1-flash-260910` 的原式为：

```text
tier("base", p * 0.03 + c * 1.2 + cr * 0.006) * (
  (
    weekday("Asia/Shanghai") == 0 ||
    weekday("Asia/Shanghai") == 6 ||
    hour("Asia/Shanghai") < 9 ||
    (hour("Asia/Shanghai") >= 12 && hour("Asia/Shanghai") < 14) ||
    hour("Asia/Shanghai") >= 18
  ) ? 0.5 : 1
)
```

当前价格展示只能提取输入 0.03、输出 1.2、缓存读取 0.006。满足非高峰条件时实际还会乘 0.5，这部分没有进入结构化价格规则展示。该问题影响展示解释，不代表后端没有执行折扣。

这 6 个模型打开编辑器时，除无法显示价格表单外，还可能触发此前发现的默认公式回写问题。文本模式应保留原式，但目前初始化和模式切换并不能可靠保证这一点，详情见 [通用兼容性报告](billing-expression-editor-compatibility-2026-11-10.md)。

## 4. 会被改写的 4 个模型

1. `deepseek-v4.1-flash-1017`：`cr * ... + p * ... + c * ...` 重新排列为 `p * ... + c * ... + cr * ...`；嵌套的默认分支展开为连续三元表达式，清理换行和外层括号。原有 0.006、0.3、1.2、0.003、0.15、0.6 系数保留。
2. `doubao-seedream-4-5-251128`：`tier("image_hd",20000)` 变为 `tier("image_hd", 20000 + p * 0 + c * 0)`。
3. `doubao-seedream-5-0-260128`：`tier("image_hd",25000)` 变为 `tier("image_hd", 25000 + p * 0 + c * 0)`。
4. `gpt-image-2-count`：`tier("image_hd",10000)` 变为 `tier("image_hd", 10000 + p * 0 + c * 0)`。

本次普通样例中，改写前后的结果一致。另针对 DeepSeek 的改写，在测试副本中将时间函数替换为固定时钟值，覆盖一周 7 天 × 每天 24 个整点 × 3 组 token，共 504 组前后对比，数值和命中档位均相同。3 个固定费用公式再各验证 3 组 token，结果也相同。这是覆盖上述样例的验证，不是所有表达式可无损转换的保证。

## 5. 与此前反馈相关的补充

**未发现存储统一保留三位小数的规则。** 本次接口原式中仍有 `0.125`、`0.625`，以及 `0.43795620437956206` 等长小数。当前快照能证明这些数值仍保留在公式原文，不能单凭本次快照判断用户某次保存前后是否曾发生过进位。

**此前贴出的复杂 metadata 回退路径没有出现在这次公开公式里。** 当前 `dreamina-seedance-2-0-fast-260128` 使用 3.3/5.6 两档，但条件是：

```text
param("content.#(type==\"video_url\").video_url.url") != nil
```

它没有检查 `metadata.content` 或 `metadata.video_url`。前述本地验证已经确认当前解析器可以保留复杂路径，因此不能把这次读取到的路径差异直接归因于自动重新生成；还需要对应保存前后的记录才能判断。

**Seedream 的 `img` 含义需要与业务意图核对。** 当前后端的 `img` 是图像输入 token 数，不是请求图片尺寸的像素数。如果 `2360000` 原意是 2.36 百万像素，这属于另一个变量语义问题，与可视化是否识别条件无关。本次没有替换该条件。

## 6. 证据与边界

- 前端：实际调用 `splitBillingExprAndRequestRules`、`tryParseVisualConfig`、`generateExprFromVisualConfig`、`parseTiersFromExpr`、请求倍率解析/生成函数。
- 后端：26 条不同原式加 22 条可生成的新式，共 48 条，执行 3 组 token 样例，共 144 次，未发生编译/执行错误；转换前后结果无差异。
- 补充检查：4 条改写公式共 513 组前后对比；时段覆盖通过替换测试副本中的时钟函数完成，没有修改运行时代码或服务器时钟。
- 公开价格页的结构化条件缺失，通过调用它实际使用的解析函数确认；没有进行浏览器像素级截图检查。
- 后端版本与首页初始资源文件名已核对一致，没有逐一下载比较所有异步 JS 文件。
- 没有修改任何线上定价、数据库或业务源码。
