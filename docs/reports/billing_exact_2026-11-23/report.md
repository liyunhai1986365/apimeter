# 本地 HTTP 精确扣费验证（2026-11-23）

以下保留修复前的三轮原始结果。修复后复跑相同的 83 个场景请使用[仓库内的验收入口](../../../scripts/billing_exact/README.md)，不再需要当时的临时目录。

**修复后复验（2026-11-23）：83/83 个场景通过，287 项检查零失败。** 独立 MySQL 5.7.44 和 Redis 上的 83 笔场景对账均一致。视频整数边界实际扣款分别为 245 和 945，小数对照仍为 552（552.5 截断）。新入口只配置这些场景实际用到的渠道，检查总数与下方历史夹具不同。

补测此前普通聊天、图片、视频成功场景仅检查余额减少的不足。每轮 83 个精确金额场景，执行三轮：**243 次通过、6 次失败**。失败集中在两个视频按次计费整数边界，三轮均复现。其余成功扣费、异步结算、并发计费和防重复扣费场景通过。

本轮仅新增测试脚本和报告，未修改业务代码、数据库结构或生产配置。使用上一轮已构建且与当前业务源码一致的二进制，SHA256 `8128a339dd975720c4035f229266c2ae52299f84b1f96aad93134c332ee45e95`。本轮没有重跑全量前后端单测，也没有将其计入本轮结果。

## 确认的问题：视频按次计费浮点乘法后截断

| 价格 | 分组倍率 | 精确乘积/截断后应扣 | 三轮实际扣费 | 每请求差额 |
|---:|---:|---:|---|---:|
| 0.0007 | 0.7 | 245 / 245 | 244、244、244 | 少扣 1 quota |
| 0.0027 | 0.7 | 945 / 945 | 944、944、944 | 少扣 1 quota |

`relay/helper/price.go:232` 先以 float64 计算 `modelPrice * QuotaPerUnit * groupRatio`，再交给 `common.QuotaFromFloatChecked`。上述结果分别落在约 `244.99999999999997` 和 `944.9999999999999`，`common/quota_math.go:62` 转为 int 时截断为 244/944。视频按次任务成功后跳过差额结算，因此这个误差成为最终扣费。

MySQL 用户/令牌、Redis、任务 quota 和日志都一致，错误发生在金额计算；本轮没有出现并发丢扣或账目之间不一致。这两个场景均为向用户少收 1 个内部 quota。

建议修复位置是按次任务的基础金额计算：用十进制完成价格、额度单位、分组倍率乘法，再按既有规则截断，并沿用溢出检查。应保留视频按次截断这一现有语义；修改全局取整规则会改变其他金额。本轮按“测试”范围保留问题，未修改业务实现。

## 初次试跑与边界说明

初次试跑曾把视频按次 552.5 的结果按四舍五入预期为 553。核对现有 `QuotaFromFloat` 及其 `42.9 → 42` 单测后，确认视频按次规则为截断，应为 552；这是测试预期错误，已修正，原始失败记录保留。它与上面精确整数 245/945 被浮点误差减 1 的问题不同。

初次试跑还因测试令牌额度 5000000 小于视频表达式预扣 7500000 而返回 403。正式三轮将隔离测试令牌额度设为 20000000，完成真实成功结算；没有修改网关预扣限制。

上游完全为本机 mock；MySQL 5.7.44 位于 `127.0.0.1:50484`，Redis 位于 `127.0.0.1:6380`，使用 DB14。每轮独立 schema，结束后删除 schema 并清空本轮 Redis 数据；应用正常退出，专用本地数据库容器继续运行。新渠道缓存等待行为保持原样。
