## 结论

发现 4 类后端问题，其中实时 WebSocket 流中扣费与最终结算衔接的问题会造成多扣，Claude 缓存归一化和实时音频变量遗漏会造成漏计或选错阶梯。以下差额已用本地 SQLite 数据库复现到钱包、令牌和消费日志，不能把此前 43 组数学算例通过理解为整个后端扣费链路正确。

四位小数价格、正常文本请求的额度换算与取整、钱包和订阅的预扣差额结算，在本次覆盖的场景中正确。

2026-11-10 初次核算未修改后端业务代码、线上定价或真实账户余额。核算基于本地代码 `43c4044e8` 和此前保存的公开定价快照；没有取得线上某个请求的原始 usage 与扣款前后余额，因此下列金额是可复现算例，不是已确认的线上损失统计。

## 验证方法与单位

文本实际调用链：

```text
PreConsumeBilling → NewBillingSession → 钱包/令牌预扣
PostTextConsumeQuota → effectiveBillingUsage → BuildTieredTokenParams
→ TryTieredSettle → SettleBilling → BillingSession.Settle
→ 钱包/令牌余额、用户/渠道累计用量、消费日志核对
```

实时请求额外覆盖 `PreWssConsumeQuota` 的流中扣款，再调用 `PostWssConsumeQuota` 最终结算。测试不访问上游模型、不发送真实付费请求。

除注明外，分组倍率为 1，`quota_per_unit = 500000`：

```text
最终配额 = round(表达式结果 / 1000000 × 500000 × 分组倍率)
美元金额 = 配额 / 500000
```

金额均以美元计。站点人民币显示汇率不改变此处的配额核算。

## 1. 高优先级：实时 WebSocket 流中费用没有抵扣最终结算，导致多扣

位置：`service/quota.go:302`、`service/billing_session.go:47`、`service/billing.go:59`。调用来源为 `relay/channel/openai/relay-openai.go:586` 的 `preConsumeUsage`，最终经 `relay/websocket.go:44` 结算。

`PreWssConsumeQuota` 直接调用 `PostConsumeQuota` 扣钱包和令牌，但不增加 `BillingSession` 中已扣的额度。连接结束时，`BillingSession.Settle` 只知道最初的预扣，按“最终费用 − 最初预扣”再次调整余额，流中已经扣的部分没有被抵扣。

使用纯文本实时用量，输入 100 token；普通模式模型倍率 1，或表达式 `tier("base", p*2)`，两者应收费都为 100 配额：

| 环节 | 钱包累计扣除 | 令牌累计扣除 |
|---|---:|---:|
| 连接开始预扣 | 1,000 | 1,000 |
| 流中收到用量，扣 100 | 1,100 | 1,100 |
| 最终应收费 100，只退回 1,000−100=900 | **200** | **200** |

最终消费日志、用户累计消费、渠道累计消费都只记录 **100**，但钱包和令牌实际扣 **200**。两个各 100 token 的用量片段，则应扣 200、实际扣 400、日志记 200。

普通倍率和表达式定价分别测试 1、2 个用量片段，4 个场景全部复现。这里的两倍来自测试中流中费用恰好等于最终费用；实际表达式价格与流中倍率价格不同时，差额不一定恰好为一倍。

建议将流中已扣费用纳入统一计费会话，并在最终结算时抵扣全部已扣款；同时核对消费日志和资金账是否一致。只改日志不能修复实际多扣。

## 2. 高优先级：Claude 缓存创建缺少 TTL 明细时丢失总数

位置：`service/billing_usage.go:145`、`service/tiered_settle.go:29`。

上游可能返回 `cache_creation_input_tokens`，但没有 `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`。`usageFromClaudeBillingUsage` 保留了总数，却没有补全明细；`BuildTieredTokenParams` 又用为 0 的明细覆盖总数，使 `cc = 0`，同时低估 `len`。

真实非流式 Claude 入口 `relay/channel/claude/relay-claude.go:754` 原样保存这份 `BillingUsage`。即使客户端收到的 OpenAI 展示 usage 已补齐明细，结算仍优先读取原始 `BillingUsage`，因此展示格式转换不能保证避开问题。

按现有转换器的规则，未指定 1h 的剩余缓存创建量归入 5m；已有 `relaykit/relayconvert/internal/shared/claude/cache.go` 的 `NormalizeCacheCreationSplit` 可供修复时参考。

使用当前公开快照的 `claude-haiku-5-5` 公式：

```text
len <= 100000
  ? tier("standard", p*0.1+c*0.5+cr*0.01+cc*0.125+cc1h*0.2)
  : tier("long_context", p*0.5+c*2.5+cr*0.05+cc*0.625+cc1h*1)
```

测试 usage：文本输入 90,000、5m 缓存创建 20,000、输出 1,000、缓存读取 0。

| 返回方式 | 后端 len / cc | 档位 | 应扣配额 | 实扣配额 | 实扣美元 |
|---|---|---|---:|---:|---:|
| 缓存总数和 TTL 明细齐全 | 110,000 / 20,000 | long_context | 30,000 | 30,000 | $0.06 |
| 只有缓存总数 | 90,000 / 0 | **standard** | 30,000 | **4,750** | **$0.0095** |

正确手算：`(90000*0.5 + 1000*2.5 + 20000*0.625) / 2 = 30000`。
实际错误手算：`(90000*0.1 + 1000*0.5) / 2 = 4750`。

另外，用当前 `claude-fable-5-1` 的 `p*10+c*50+cr*0.25+cc*12.5+cc1h*20`，文本输入 1,000、5m 创建缓存 3,000、输出 500，只给缓存总数时：应扣 **36,250（$0.0725）**，实际扣 **17,500（$0.035）**。

这些算例的钱包扣款、令牌扣款和日志金额彼此一致，但都使用了错误的计价参数。与问题 1 的“日志和余额不一致”不同，单纯对账不能发现这类少收。

## 3. 实时音频表达式没有获得音频、缓存变量

位置：`service/quota.go:314`。

`PostWssConsumeQuota` 只向表达式传入 `P/C/Len`；同一份 `RealtimeUsage` 中虽有音频和缓存明细，却没有传入 `ai/ao/cr`，也没有按表达式引用从 `p/c` 排除相应子类别。

独立验证最终结算入口，暂不加入问题 1 的流中扣款：输入 1,000，其中音频 800；输出 500，其中音频 400。

| 表达式 | 正确配额 | 最终结算实际配额 |
|---|---:|---:|
| `p*2+c*10`，全部按兜底价格 | 3,500 | 3,500 |
| `p*2+c*10+ai*20+ao*40`，音频单独定价 | **16,700** | **3,500** |
| `ai*20+ao*40`，仅收音频费用 | **16,000** | **0** |

第二行正确手算：`(200*2 + 100*10 + 800*20 + 400*40)/2 = 16700`。

上表用于隔离最终结算参数问题，不代表加入流中扣费后的整个 WebSocket 连接一定少收这么多；问题 1 和本问题可能叠加。应在同一次修复中统一实时用量归一化和已扣额度管理。

当前公开定价快照的 30 个表达式模型中，没有名称含 realtime/audio 的模型；不能据此认定线上已经发生此类实时音频误计费。

## 4. Claude 未显式定价的缓存不会回归 p，跨格式价格不一致

位置：`service/tiered_settle.go:25`、`:50`。

公式 `tier("base", p*3+c*15)`，等价用量为文本输入 800、缓存命中 200、输出 500：

| 上游格式 | 原始输入字段 | 实际 p | 实扣配额 |
|---|---:|---:|---:|
| OpenAI | prompt_tokens=1,000，包含缓存 | 1,000 | **5,250** |
| Claude | input_tokens=800，缓存另列 | 800 | **4,950** |

按文档中“p 是未单独定价子类别的兜底变量”和“表达式无需关心上游格式”的定义，两者应都为 5,250。当前 Claude 分支没有把未单独定价的缓存加回 p，少计 300 配额（$0.0006）。

文档同时写了“Claude 不做任何减法 / no adjustment needed”，实现也遵循这一句，因此这里存在语义定义不完整的问题。修复时应明确采用统一兜底语义，并对希望免费缓存的公式保留 `cr*0` 等显式写法，避免悄悄改变管理员对省略变量的理解。

快照中的两个 Claude 表达式均已显式包含 `cr/cc/cc1h`，所以本项简化公式案例不能直接套到它们；它们需要重点检查的是问题 2。

## 正常算例与资金结算

四位小数公式：`tier("base", p*0.1234+c*0.5678+cr*0.0123)`。

OpenAI 原始输入 1,000,000，含缓存 200,000；输出 100,000：

```text
p = 800000
原始结果 = 800000*0.1234 + 100000*0.5678 + 200000*0.0123 = 157960
最终配额 = 78980 = $0.15796
```

| 场景 | 实际最终扣款 | 结果 |
|---|---:|---|
| 预扣 100,000，退回 21,020 | 78,980 | 钱包、令牌、累计消费、日志一致 |
| 预扣 1,000，补扣 77,980 | 78,980 | 一致 |
| 分组倍率 0.37 | 29,223 | 最后对 29,222.6 配额取整 |
| 分组倍率 0，已有预扣 | 0 | 全额退回 |
| Claude 明确提供 5m/1h 缓存明细并单独定价 | 58,425 | 与手算一致 |

单独验证资金会话：钱包、订阅分别预扣 1,000，然后结算 0、500、1,000、2,000，8 个场景全部通过；重复调用同一会话的 `Settle` 不重复扣款，结算完成后的 `Refund` 不回滚已完成结算。订阅测试同时确认钱包余额不变、订阅已用额度与令牌扣款一致。

这不等于已覆盖请求失败时的异步退款、数据库提交失败恢复、进程崩溃恢复或所有提供商的流式 usage。
