# 表达式计费核算（2026-11-10）

> 后续已扩展到实际扣款链路，并复现后端问题，见 [后端实际扣费链路核算](backend-billing-verification-2026-11-10.md)。本报告的 43 组结果仅适用于下述选定数学算例，不能外推为全部后端结算正确。

## 结论

本次 43 组独立十进制算例，经过真实后端的 usage 归一化、表达式执行、分组倍率、额度换算和取整后，均与预期一致。四位小数的价格系数可正确参与计费，没有被先四舍五入成三位。

本轮选定算例发现的问题集中在前端试算，以及公式条件与业务意图可能不一致。这些算例的后端计算结果与所配置公式一致，不代表其他 usage 返回形式或实际扣款流程已经正确，也不代表公式一定表达了期望的业务价格。

本次仅核算，未修改应用代码或线上配置，未发起真实付费请求。所用线上价格来自本轮对话此前保存的公开接口快照；未核对某个用户的实际消费日志、上游 usage 或余额变动。

## 换算规则

快照的 `quota_per_unit = 500000`。以下金额按分组倍率 1、美元计算：

```text
美元理论费用 = 表达式结果 / 1000000 × 分组倍率
扣除配额 = round(美元理论费用 × 500000)
实际配额对应美元 = 扣除配额 / 500000
```

取整只发生在最后的整数配额上，不是在价格系数或美元金额的小数点第四位上。例如 157.96 的表达式结果，对应理论 $0.00015796、78.98 配额，实际扣 79 配额，即 $0.000158。

四位小数例的手算过程：

```text
p = 1000000 - 200000 = 800000
原始结果 = 800000 × 0.1234 + 100000 × 0.5678 + 200000 × 0.0123
         = 98720 + 56780 + 2460
         = 157960
美元费用 = 157960 / 1000000 = 0.15796
配额 = 0.15796 × 500000 = 78980
```

## 问题一：前端试算结果不等于最终扣费

`web/default/src/features/pricing/lib/tier-expr.ts` 的 `evalExprLocally` 直接返回表达式结果；编辑器以“估算配额费用”展示。它没有做 `/1000000 * QuotaPerUnit` 的配额转换。

此外，前端将输入数直接赋给 `p`，并把缓存数加进 `len`。如果按 OpenAI usage 的原始 prompt_tokens 填入，缓存会重复计算，可能选错长上下文档。前端 `param`、`header`、`response` 也没有真实请求上下文。

| 同一组输入 | 前端显示的“配额费用” | 后端实际配额 | 差异原因 |
|---|---:|---:|---|
| 上述四位小数算例 | 182640 | 78980 | 缓存未从 p 扣除，且未做配额换算 |
| Seedream 普通档 | 43000 | 21500 | 未做配额换算 |
| GPT-5.4 输入 272000、缓存 200000、输出 1000 | 1482500，long_context | 122500，standard | len 被错误加到 472000，同时缓存和单位处理不同 |
| Seedance 视频输入、输出 100000 | 560000，无视频档 | 165000，视频档 | 前端 param 始终返回 null，且未做配额换算 |

该函数仅供编辑器试算展示，实际后端结算不读取其结果。因此这些差异不能用于断言线上后端按前端数字多扣了费用。

## 问题二：用户此前提供的视频路径有漏判

此前提供的复杂 GJSON 路径，在以下请求中会选中无视频档：

```json
{
  "content": [{ "type": "text", "text": "prompt" }],
  "metadata": { "video_url": "https://example.invalid/test.mp4" }
}
```

真实后端结果（输出 100000 token）：

- content 中直接有视频：视频档，$0.33。
- 只有 metadata.video_url：视频档，$0.33。
- metadata.content 中有视频：视频档，$0.33。
- content 有文字，同时 metadata.video_url 有视频：无视频档，$0.56。

如果业务要求任意一个位置存在视频都使用视频档，这条条件需要修正。当前路径先选取非空内容集合，文字 content 会阻止后续 metadata 视频被命中。这是此前用户提供的公式，不是本次快照中 Dreamina Fast 使用的简化 content 路径。

## 问题三：图片阈值和周末价格需按业务意图确认

`img` 是图片输入 token 数，不是输出图片像素。实测请求参数为 `4096x4096`、但 usage 的图片输入 token 为 0 时，当前 Seedream 公式仍收 $0.043。若目的是按输出分辨率区分 $0.043/$0.086，应该基于请求或响应中的尺寸计算像素，并确认实际字段。

DeepSeek v4-flash / v4-pro 的公式仅判断小时，不判断星期，因此周六 10 点仍是 peak；v4.1-flash 和 v4-1-flash-260910 才包含周末相关条件。后端严格按各自公式执行，本次未修改这些条件。
