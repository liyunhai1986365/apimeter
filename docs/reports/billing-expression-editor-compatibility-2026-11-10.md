# 表达式定价：后端与前端兼容性排查报告

排查日期：2026-11-10。代码基线：`43c4044e8`（`v1.0.24-43c4044e8`）。主要范围：`web/default`、`pkg/billingexpr`、定价配置保存与结算入口。本次只做排查和报告，没有修改业务实现、保存定价或操作线上服务。

## 1. 结论

你补充的现象是“原来的内容不显示，只显示默认的”。代码中存在与这一现象吻合的覆盖路径：**初始化和数据回填过程可能把表单中的原表达式替换为零价格默认公式。** 不兼容语法会触发其中一条路径，组件先挂载、表达式后到也有独立风险。因此，需要同时处理语法兼容和编辑器状态同步。

具体发现：

1. **后端与前端使用不同的解析方式。** 后端运行完整的 expr-lang 表达式；可视化编辑器只接受能拆成价格字段、条件和倍率的有限格式。后端可以计算，并不代表前端能还原成表格。
2. **不兼容时的原文保留存在缺陷。** 编辑器有切换到文本模式的代码，但初始化回写可能先覆盖原文；手动从文本模式切回可视化模式时，也会在解析失败后使用默认配置。
3. **部分“解析成功”的表达式也不安全。** 重复计价项、免费分支、字符串条件、显式零价缓存项在重新生成后，已经复现计算结果或计费语义改变。
4. **价格展示和本地试算又是另外两套逻辑。** 价格展示可能漏项或显示部分系数；本地试算采用 JavaScript，与后端 expr-lang 不完全等价。

随后收到的实际视频定价表达式，已确认当前 `default` 前端可以解析，不能归因为该公式语法不受支持，具体结果见第 10 节。本报告已复现“加载后变默认”的状态变化；组件部分使用源码提取后的状态流程模拟，未进行浏览器端完整交互复现。后端执行、前端纯解析函数和转换后的数值差异均已实际运行验证。

## 2. 四套逻辑分别负责什么

| 环节 | 当前实现 | 能力与限制 |
| --- | --- | --- |
| 后端执行 | `expr.Compile` / `expr.Run`，附加计费变量、请求函数和轨迹采集 | 支持表达式运算、条件、函数、局部变量等；`tier()` 用于记录档位，不是执行必需条件 |
| 可视化编辑 | `tryParseVisualConfig` → `generateExprFromVisualConfig`，另加请求倍率解析 | 把有限格式转成表单，再生成字符串；没有全面的等价性保障 |
| 价格/日志单价展示 | `parseTiersFromExpr` 等 | 搜索 `tier("` 和 `变量 * 数字`，不是解释执行；可能只识别公式的一部分 |
| 本地试算 | `evalExprLocally` → `new Function` | 以 JavaScript 求值；请求参数和响应固定为空，不能等同于真实结算 |

后台另一处“模型编辑”入口使用普通文本框，没有经过同样的可视化反向解析。这也解释了为什么相同公式可能在一个入口能编辑，在另一个入口显示不完整或变成默认值。

## 3. 为什么会显示默认配置

### 3.1 初始化回写覆盖原文：优先修复

位置：`tiered-pricing-editor.tsx:1695–1757`，`tier-expr.ts:204–209`。

当前流程：

1. `editorMode` 初始固定为 `visual`。
2. 对不支持的表达式，`tryParseVisualConfig` 返回 `null`。
3. 在这一轮渲染中，`generateExprFromVisualConfig(null)` 返回 **`p * 0 + c * 0`**。
4. 初始化 effect 虽然安排切换到文本模式，另一条同步 effect 仍使用这一轮的默认公式，调用 `onBillingExprChange` 回写父表单。
5. `initRef` 又在后置的 `modelName` effect 中重置。父子状态再次同步时，默认公式可能被重新读入 `rawExpr`，最终原文丢失。

提取实际组件的 Hooks 代码，模拟父组件通过 `setBillingExpr` 接受回写，得到：

| 初始表达式 | 后端能否执行 | 状态稳定后的表单表达式 |
| --- | --- | --- |
| `tier("base", p * 2 + c * 4)` | 能 | 保持原式 |
| `p * 2 + c * 4` | 能 | `p * 0 + c * 0` |
| `tier("base", max(p * 2, 1000) + c * 4)` | 能 | `p * 0 + c * 0` |
| 不带空格的请求倍率组合 | 能 | `p * 0 + c * 0` |

因此，“存在文本模式兜底”并不能证明原表达式会被保留。

**影响边界：这里首先覆盖的是编辑器和父表单状态。** 本次没有发现仅打开该编辑器就直接写数据库的调用；继续提交并保存配置，才可能把错误公式持久化。保存路径见 `model-pricing-sheet.tsx:729`、`model-ratio-visual-editor.tsx:822`。

### 3.2 切回可视化时直接使用默认值

位置：`tiered-pricing-editor.tsx:1777–1799`。

`handleModeChange('visual')` 在反向解析失败后直接调用 `createDefaultVisualConfig()`，没有阻止切换或保留原文为当前计费来源。之后的同步 effect 会把默认公式写回父表单。

这条路径不依赖初始化时序：复杂公式在文本模式可见，也可能在切回可视化后变成默认值。

### 3.3 后到的数据、同一实例切换模型也有风险

组件把 `initRef` 的重置放在初始化 effect 后面，且根据 `effectiveExpr` 自动回写父组件。`model-pricing-sheet.tsx:904` 没有用模型标识给编辑器设置 `key`。

在“组件不卸载、直接接收新 props”的模拟条件下：

- 先挂载空表达式，再传入有效计价公式，最终可能仍是默认公式。
- 从模型 A 切到模型 B，旧的 A 表达式可能被回写到 B 的表单。

实际页面是否走这一时序，取决于弹窗与 Tabs 的挂载方式，需要浏览器交互验证。它应作为同一状态同步问题的回归场景，不能只靠扩大语法支持解决。

## 4. 后端能识别、前端不能完整处理的形式

下表依据实际运行的样例。“可视化支持”指反向解析函数能返回表单配置，不代表已经保证重新生成后等价。

| 表达式形式 | 后端 | 可视化反向解析 | 价格展示 |
| --- | --- | --- | --- |
| `tier("base", p * 2 + c * 4)` | 支持 | 支持 | 正常 |
| `p * 2 + c * 4`，没有 `tier()` | 支持 | 不支持 | 无结构化档位 |
| `tier("base", 2 * p + 4 * c)` | 支持 | 不支持 | 找到档位，但提取价格为 0 |
| `tier( "base", p * 2 + c * 4)` | 支持 | 支持 | 无档位；展示搜索依赖紧邻的 `tier("` |
| `tier ("base", ...)`、单引号标签 | 支持 | 不支持 | 无结构化档位 |
| `tier("base", max(p * 2, 1000) + c * 4)` | 支持 | 不支持 | 只提取部分系数，丢失最低消费语义 |
| `tier("base", p / 2 + c * 4)` | 支持 | 不支持 | 输入价格无法正确提取 |
| `p ^ 2`、`let`、`and`、`in` 等语言语法 | 样例执行成功 | 不支持这些结构 | 可能只显示内部部分档位 |
| `pixels(param("size"))` / `response(...)` 作为条件 | 有对应请求/响应时支持 | 不支持这些条件 | 能提取内部价格，条件说明缺失 |
| `param("parameters.duration") * 0.1 * 1000000` 放在 `tier` 内 | 支持 | 支持这个固定路径和形式 | 可提取秒价 |
| 上例改用 `param("duration")` | 有对应字段时支持 | 不支持 | 秒价无法提取 |
| `0.1 * 1000000`，没有 `tier()` | 支持 | 不支持 | 无结构化档位 |
| `tier("base", 0.1 * 1000000 + p * 2)` | 支持 | 支持 | 漏掉固定每次费用 |
| `v1:tier(...)` | 支持 | 支持，但重新生成移除前缀 | 可解析；本地试算会报语法错误 |
| `v2:tier(...)` | 当前不支持 | 却会剥去前缀并接受 | 也会剥去前缀并显示 |
| 普通完整嵌套三元档位 | 支持 | 部分形式支持 | 条件提取不完整 |

后端不是任意字符串都能执行：语法、类型、返回数值要求和运行时输入仍有约束。请求/响应样例成功只说明相应输入下成立，不能保证缺少字段时也能执行。

请求倍率还有更严格的格式依赖：

```text
(tier("base", p * 2 + c * 4)) * (param("service_tier") == "fast" ? 2 : 1)
```

这个格式可以拆出倍率。以下形式后端仍能计算，但前端无法正常拆出倍率配置：

- 删除乘号和三元运算符两侧空格。
- 把最后的 `1` 写成 `1.0`。
- 使用 `(param("n") != nil && param("n") > 2 ? 2 : 1)`。
- 使用参数存在判断加 `has(...)` 的组合。

最后两种还是当前前端生成器能够生成的形式。实测 `buildRequestRuleExpr` 生成数字比较规则后，再交给 `tryParseRequestRuleExpr` 会返回 `null`。原因是倍率解析先拆开 `&&`，把本应整体识别的“存在判断 + 比较”分成了两段；档位条件解析已有相邻片段合并逻辑，倍率解析没有。

位置：`billing-expr.ts:467`、`:485`、`:644`、`:701`、`:890`；对照 `tier-expr.ts:421`。

## 5. 解析成功后仍然改变价格的已验证问题

以下数值是**表达式原始返回值**，还没有执行 `/ 1000000 × QuotaPerUnit × 分组倍率`，不是直接展示的人民币、美元或最终扣费额度。除缓存案例外，使用 `p=50`、`c=20`、`len=50`。

| 问题 | 原表达式 | 重新生成结果或变化 | 后端计算前 → 后 |
| --- | --- | --- | --- |
| 重复 token 项被覆盖 | `tier("base", p * 2 + p * 3 + c * 4)` | `tier("base", p * 3 + c * 4)` | **330 → 230** |
| 重复常数项被覆盖 | `tier("base", 100000 + 200000 + p * 2)` | 只保留 `200000` 固定部分 | **300100 → 200100** |
| 免费真分支丢失 | `len < 100 ? 0 : tier("base", p * 2 + c * 4)` | 变成无条件的付费档位 | **0 → 180** |
| 嵌套免费分支丢失 | `len < 100 ? (c < 50 ? 0 : tier("b", p * 2)) : tier("c", p * 3)` | 内部 `c < 50` 免费分支消失 | **0 → 100** |
| 字符串被改成数字 | `param("code") == "123" ? tier("high", p * 5) : tier("base", p * 2 + c * 4)` | 条件变为 `param("code") == 123` | 请求 `code` 为字符串 `"123"` 时，**250 → 180** |
| Header 字符串被改成数字 | 基础价格乘 `(header("code") == "123" ? 2 : 1)` | `"123"` 变成 `123`，不再匹配 | **360 → 180** |

代码原因：

- `tier-expr.ts:368` 把每一项写入同一个字段，重复项采用覆盖而非累计，也没有拒绝不可靠的转换。
- `tier-expr.ts:466` 收集档位时跳过零成本叶子；没有完整保留相应路径的排除条件。
- `billing-expr.ts:858` 根据文本内容推断数字/布尔值，丢失输入原本是字符串这一类型信息。

**缓存零价格尤其不能当作无用项删除。**

```text
原式：tier("base", p * 2 + c * 4 + cr * 0)
生成：tier("base", p * 2 + c * 4)
```

在后端，引用 `cr` 会触发缓存 token 从输入 `p` 中扣除。对于非 Claude 的 usage：`prompt_tokens=1000`、`cached_tokens=400`、输出为 0：

- 原式引用 `cr`：归一化后 `p=600`，表达式返回 **1200**。
- 新式删除 `cr`：`p=1000`，表达式返回 **2000**。

本例使用后端实际编译器，并提取执行了当前 `BuildTieredTokenParams` 函数源码。`UsedVars` 的变化也已实测确认。相关位置：`tier-expr.ts:191`、`compile.go:253`、`service/tiered_settle.go:25`。

这些变化可能在初始化自动生成公式时就进入表单，不必等用户主动修改价格字段。

## 6. 价格展示和试算的额外偏差

**价格展示没有验证完整公式是否已经识别。** 例如：

- `p * 2 + p * 3`：后端合计输入单价是 5；价格展示取第一项显示 2；可视化编辑取最后一项显示 3。
- `p * 2 * 3`：后端实际系数是 6，展示只提取 2。
- `2 * p`：提取不到输入单价，内部按 0 处理；UI 又可能过滤掉该项。
- `tier( "base", ...)`：可视化能解析，价格展示却找不到档位。

`DynamicPricingBreakdown` 在完全找不到档位时已有“无法解析结构化定价”的原文回退。但只要找到了某个档位，就可能进入部分解析结果的展示，不能把缺少的价格项视为真实零价。日志中的部分单价说明也依赖这一解析器；最终结算金额应以服务端结算数据为准。日志请求倍率已有服务端轨迹来源，不应把其与公开价格页的字符串解析混为一谈。

位置：`billing-expr.ts:285`、`:319`、`:434`，`dynamic-pricing-breakdown.tsx:220`，`usage-logs/lib/format.ts:393`。

**本地试算采用不同语言和不同输入。**

| 样例/因素 | 后端 | 本地试算 |
| --- | --- | --- |
| `p ^ 2`，`p=50` | 乘方，2500 | JavaScript 按位异或，48 |
| `v1:tier(...)` | 识别版本前缀 | `Unexpected token ':'` |
| `let`、`and` | 本次样例执行成功 | JavaScript 语法错误 |
| 请求字段、Header、响应字段 | 从实际输入读取 | `param/response` 返回 `null`，`header` 返回空串 |
| 时长费用，实际 duration=3 | 按 3 秒计算 | 读取不到时长，本例返回 0 |
| 缓存等分类 token | 按表达式引用的变量和 usage 语义归一化 | 没有等价的归一化过程；`len` 还固定叠加缓存数量 |
| 请求倍率 | 完整表达式参与执行 | 编辑器传入的是拆分后的基础表达式，已拆出的倍率不进入试算 |
| 金额单位 | 结算阶段做额度转换 | 返回原始公式数值，界面却标作预估额度 |

因此，当前试算适合有限的公式预览，不能作为真实结算一致性的校验器。

位置：`tier-expr.ts:573`、`tiered-pricing-editor.tsx:1414`、`:1736`、末尾 `CostEstimator` 调用，以及 `pkg/billingexpr/settle.go:8`。

## 7. 保存校验与文档存在落差

设计文档 `pkg/billingexpr/expr.md` 写到保存时会编译并进行冒烟校验。但本次全局搜索发现：

- `SmokeTestExpr` 有定义，未找到调用点。
- 当前通用 option 保存路径中，`validateOptionValue` 没有校验表达式。
- `billing_setting` 的配置后处理仅清理相关缓存。
- 当前真实存储键是 `billing_setting.billing_mode` / `billing_setting.billing_expr`，文档中的旧名称需要更新。

所以应区分三件事：**保存成功、后端在某组输入下执行成功、前端能无损编辑。** 目前三者并不等价。即使补上语法编译校验，零价格默认公式本身也合法，仍不能替代前端的原文保护。

位置：`setting/billing_setting/tiered_billing.go:73`、`model/option.go:237`、`:250`、`:686`，`controller/option.go:474`。

## 8. 建议的修复顺序

| 优先级 | 修复内容 | 验收标准 |
| --- | --- | --- |
| P0 | 修复初始化与 props 同步；原文作为计费来源，加载过程不触发用户修改式回写 | 复杂公式打开、关闭、重新打开后原文不变；后到数据和切换模型正确 |
| P0 | 解析失败留在文本模式，禁止静默切成默认价格；保留完整请求倍率 | 不支持的公式仍完整可见；切换模式不丢价格、条件、倍率 |
| P0 | 对不能证明无损的转换拒绝可视化，包括重复项、零价分类、免费分支、字符串类型 | 本报告的变价案例要么原样保留，要么明确拒绝转换 |
| P1 | 统一可视化与展示的受支持语法解析，保留类型、显式字段和分支语义 | 空格、引号等无关格式不影响识别；未知部分不显示成零价 |
| P1 | 修复倍率生成与解析的往返一致性 | 自己生成的数字比较/包含规则，重新打开后仍可正确识别 |
| P1 | 接入后端保存编译校验，更新设计文档 | 无效语法不能保存；需要请求数据的公式有明确验证边界 |
| P2 | 让试算复用后端执行及 token 归一化，支持请求/响应样例输入 | 同输入、同版本、同单位下与实际结算一致 |

不建议承诺“所有合法后端表达式都能转成表格”。任意表达式的可视化转换范围很大。更合适的产品规则是：**支持的子集可视化；其他合法表达式完整保留在文本模式，并显示清晰原因。**

语法编译与执行试算也应分开。涉及必填请求字段的公式，不应因为通用空请求样本不能执行就被一概认定为非法。用于执行校验的请求样例、预消费/结算阶段和返回值范围需要明确。

## 10. 用户实际提供的视频公式验证

原式：

```text
param("[content,metadata.content,[metadata.video_url]|@flatten]|#(#>0)|[#(type==\"video_url\").video_url.url,#(>\"\")]|#(>\"\")") != nil ? tier("480_720p_video_input", c * 3.3) : tier("480_720p_no_video_input", c * 5.6)
```

**这条原式在当前仓库的 `default` 前端可以解析，后端也可以执行。** 前端能保留完整 GJSON 路径，包括转义引号，并还原以下配置：

| 档位 | 条件 | 输入系数 | 输出系数 |
| --- | --- | --- | --- |
| `480_720p_video_input` | 请求参数路径存在，即 `param(...) != nil` | 0 | 3.3 |
| `480_720p_no_video_input` | 默认分支 | 0 | 5.6 |

可视化重新生成时给两个档位补入 `p * 0`；本次 12 组请求样例中，原式与生成后公式执行结果全部一致，共执行 24 次。单独的价格展示解析也能提取两个输出价格，但不会还原这条请求路径条件的友好说明。

状态流程模拟有两个不同结果：

- 初始 props 就带有这条完整表达式：最终保持可视化模式和正确的两档配置。
- 先用空表达式挂载，再把这条表达式作为新 props 传入：最终可能被覆盖为 `p * 0 + c * 0`。

因此，针对用户这条原式，应优先验证页面的初始化/数据回填路径，以及线上实际使用的前端是否与当前 `default` 代码一致。不能仅凭路径复杂就判断“不支持”。尚未取得生产浏览器的状态轨迹，不能把上述模拟当作生产时序已被确认。

**公式的请求判断还存在一个独立的行为问题。** 以下是后端实测匹配结果：

| 请求内容 | 实际使用的系数 |
| --- | --- |
| `content` 中有非空 `video_url.url` | 3.3 |
| 只有 `metadata.content` 中有视频 | 3.3 |
| 只有字符串形式的 `metadata.video_url` | 3.3 |
| `content` 为空数组，`metadata.video_url` 有视频 | 3.3 |
| 无视频，或视频 URL 为空字符串 | 5.6 |
| `content` 有文本，同时 `metadata.video_url` 有视频 | **5.6，未识别到后面的 metadata 视频** |
| `content` 有文本，同时 `metadata.content` 有视频 | **5.6，未识别到后面的 metadata 视频** |
| `metadata.video_url` 是 `{ "url": "..." }` 对象 | 5.6 |
| `content` 是非空普通字符串数组，例如 `["not-a-video-url"]` | **3.3，并未检查它是否真是视频地址** |

原因是中间的 `#(#>0)` 先选取第一个非空候选集合，而不是遍历所有来源寻找视频。前面的 `content` 有文本时，会阻止后续 metadata 来源参与；后续 `#(>"")` 又允许普通非空字符串匹配。

如果业务希望“任意来源存在视频就使用 3.3”，需要调整这段 GJSON 条件；这与编辑器显示问题是两个独立事项。档位名中的 `480_720p` 也只是标签，原式没有检查实际分辨率，3.3/5.6 是输出变量 `c` 的系数。

具体原文、解析配置、状态轨迹和 12 组后端样例已追加到 JSON 附件的 `user_expression_case`。本次仍未修改业务实现。

## 11. 保存后重新打开：公式改写与小数精度

用户进一步反馈：保存表达式、重新打开后，公式本身也发生了变化。因此，不能用试算区域 `toLocaleString()` 默认显示最多三位小数来解释所有现象。

当前代码确实会重新生成表达式。`tryParseVisualConfig` 将系数转换为 JavaScript `Number`，打开编辑器后采用可视化模式，`generateExprFromVisualConfig` 再把数字写回公式，随后 effect 同步到父表单。其间可能补入 `p * 0`、去掉数字尾零、规范化写法；第 5 节中的不可靠转换还可能改变实际计算结果。

针对普通小数系数，模拟“进入文本模式、修改公式、序列化保存数据、重新挂载编辑器”，结果如下：

| 原始输出项 | 重新打开后的输出项 | 结论 |
| --- | --- | --- |
| `c * 3.333` | `c * 3.333` | 没有进位 |
| `c * 3.3333` | `c * 3.3333` | 没有截为三位小数 |
| `c * 3.3338` | `c * 3.3338` | 没有变成 `3.334` |
| `c * 3.300` | `c * 3.3` | 文本改变，数值相同 |
| `c * 0.001` | `c * 0.001` | 保留 |
| `c * 0.0004` | `c * 0.0004` | 保留；试算结果若恰为该值则可能显示为 0 |
| `c * 3.3330000000000000001` | `c * 3.333` | 转为浮点 Number 后丢失过长的十进制字面量精度 |

本次还实际执行了后端 `UpdateConfigFromMap` → `ConfigToMap`，上述 7 条原式的字符串全部原样保留，包括尾零和很长的小数字面量。另一处普通文本模型编辑的 `syncModelPricingMaps` 也保留原式。未调用线上接口或真实数据库。

保存路径的源码检查未发现表达式字符串统一保留三位小数的规则；`pricing-format.ts` 的数字格式化用于普通倍率价格字段，没有在表达式保存路径中使用。价格输入框的 `step=0.01` 控制原生数字输入的步进，输入及失焦处理本身使用 `Number`，没有按两位或三位调用取整函数。

**当前可确认公式会被改写，但尚未复现普通三位/四位系数在保存后自动进位。** 还需要用户提供一组实际的“保存前数值 → 重新打开后的数值”，才能区分数字格式规范化、原生输入步进、表达式转换损失或其他代码/部署版本差异。组件测试仍是状态流程模拟，不能代替线上浏览器的保存请求与回填数据核对。

证据已追加到 JSON 附件的 `precision_save_reopen`。
