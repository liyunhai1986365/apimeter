# 旧 slave 与新 master 混跑兼容性实测

测试日期：2026-09-13。持续请求窗口：北京时间 11:34:25 至 11:37:45，约 201 秒；随后完成旧版重启与补充业务测试。

## 结论

在本次隔离环境、备份数据和模拟业务负载下，新 master 的数据库迁移没有打断旧 slave 的已测业务。持续请求 1,251 次全部成功，743 次模型调用的用户扣费、令牌扣费和消费日志完全一致；跨越迁移的 90 秒 SSE 完整结束。新 master 停止后、旧 slave 再次重启后，旧版也能正常读取升级后的数据库并处理请求。

但不能据此认定新旧版本可以完全无感混跑，实际发现两个控制台会话兼容问题：

1. **旧版登录 Cookie 访问新版 `/api/user/self` 返回 401。** 相同 Cookie 访问旧版正常。将已登录用户的控制台请求切到新版，会遇到认证不兼容。
2. **新版退出登录后的会话，在旧版仍可被接受。** 新版登录得到的同一组 Cookie/Bearer 凭据，在新版退出登录后，重放至新版返回 401，重放至旧版返回 200。新旧版本没有统一执行会话撤销语义。

这些发现来自真实镜像的 HTTP 请求，不是仅根据源码推测。第二项重放使用的是完整的新版本凭据组合，没有分别拆测 Cookie 与 Bearer 的独立行为。

## 执行过程与结果

先启动旧 slave，完成注册、登录、创建渠道/令牌及单次请求基线。随后持续请求旧版 60 秒，在一条 90 秒 SSE 仍运行时启动新 master，待其完成迁移并就绪后，继续向两版发送请求。普通调用模拟 20 个输入 Token、10 个输出 Token；短 SSE 返回完整结束标记和用量。

| 发起阶段 / 节点 | 持续请求数 | 失败数 |
| --- | ---: | ---: |
| 基线 / 旧 slave | 293 | 0 |
| 新 master 启动及迁移 / 旧 slave | 12 | 0 |
| 新旧混跑 / 旧 slave | 668 | 0 |
| 新旧混跑 / 新 master | 278 | 0 |
| 合计 | 1,251 | 0 |

按请求开始时的阶段归类，因此基线中的一条长 SSE 实际跨越了迁移及混跑阶段。失败统计同时检查 HTTP 状态、JSON 业务错误、模型返回内容和 SSE 完整结束，未以请求重试掩盖失败。

新 master 从发出容器启动命令至 `/api/ready` 成功约 **2.196 秒**，包含启动、迁移和就绪轮询，不能解释为纯 SQL 执行耗时或生产停机时间。

| 旧 slave 操作 | 基线 P95 | 混跑 P95 | 混跑最大耗时 |
| --- | ---: | ---: | ---: |
| 普通模型调用 | 56.8 ms | 56.8 ms | 95.5 ms |
| 短 SSE，全流耗时 | 312.9 ms | 312.7 ms | 314.3 ms |
| 个人信息 | 4.0 ms | 4.6 ms | 5.6 ms |
| 使用日志列表 | 5.7 ms | 6.5 ms | 7.5 ms |
| 令牌列表 | 7.6 ms | 8.4 ms | 8.7 ms |

长 SSE 实测 90.046 秒，HTTP 200，收到完整内容和 `[DONE]`。普通调用与短 SSE 的时延包含模拟上游的固定等待，不能当作真实供应商性能数据。

### 计费核对

主测试窗口内共 743 次成功模型调用，每次应扣 10 个内部额度单位：

- 用户余额：99,999,980 → 99,992,550，减少 **7,430**。
- 用户已用额度：20 → 7,450，增加 **7,430**。
- 用户请求次数：2 → 745，增加 **743**。
- 令牌余额、已用额度变化与用户一致。
- 对测试用户及主测试日志 ID 窗口查询：**743 条消费日志，额度合计 7,430，单条最小/最大均为 10**。
- 相同窗口内没有重复的非空 `request_id`。

余额核对在停止持续请求并等待批量更新落库后执行，排除了后续重启检查和补充图片任务的调用。

### 图片任务补测

主测试中图片提交曾返回 503：模拟渠道未显式声明 `openai.image.generations` 协议，任务没有创建。该失败保留在原始结果，未算作升级故障或已通过测试。

主测试结束后，在专用模拟渠道补充 `openai.chat` 与 `openai.image.generations` 协议并启动新 master，单独执行了以下验证：

- 旧版提交异步图片任务，新旧版均能读取任务，最后均返回 `succeeded` 且有结果。
- 新版提交异步图片任务，新旧版均能读取任务，最后均返回 `succeeded` 且有结果。
- 数据库中的两个测试任务均为 `SUCCESS`、进度 `100%`，记录额度均为 20,000。

**该补测验证的是迁移后跨版本任务兼容，没有覆盖图片任务执行途中发生 DDL，也没有覆盖进程停止时的后台任务接管。**

## 数据库变化与错误检查

业务库从 60 张表变为 66 张，新增 `agent_announcements`、`auth_flows`、`authz_roles`、`casbin_rule`、`external_identity_claims`、`user_sessions`。修改了 `crypto_payments`、`midjourneys`、`tasks`、`tokens`、`users` 五张既有表，没有删表。日志库仍为 9 张表，结构不变。

完整差异在 `schema-diff.txt`，比较忽略表级自增计数器变化。新旧应用日志中均未检出缺字段、缺表、死锁、锁等待超时或 panic 的匹配错误。旧版日志无数据库迁移启动记录。没有做迁移期间数据库元数据锁的连续采样。

## 范围限制与发布含义

这是指定两个镜像、指定备份、MySQL 5.7.43 和有限模拟负载下的一次回归。没有覆盖生产峰值、真实上游异常退款、全部管理接口、支付、完整账单流程、WebSocket、其他数据库版本，也没有通过 Caddy 实际切流。

业务层结果支持继续推进 API 代理服务的滚动升级验证；控制台流量直接在两版之间切换仍有已证实的会话问题。需要先解决会话格式及撤销行为的一致性，再验证实际入口切流，不能仅根据健康检查或上述 1,251 次成功请求宣布完全零影响。
