# 智能路由失败重试

`group_policy.type=routing_strategy` 的四种策略（`smart_auto`、`price_first`、`speed_first`、`success_first`）共用以下机制，只有候选分组的排序方式不同。

| 限制 | 行为 |
| --- | --- |
| 组内重试 | `min(RetryTimes, 3)`，首次请求另计，每组最多 4 次尝试 |
| 整次请求 | 最多 12 次尝试，切换分组、切换备选模型不会重置总预算 |
| 重试窗口 | 请求开始 2 分钟后不再启动新尝试，不截断已经正常运行的长响应 |
| 重试间隔 | 100–900 毫秒递增退避并加入随机抖动，客户端取消时立即停止等待 |

系统 `RetryTimes=0` 时，每个候选分组仍可尝试一次。智能策略天然允许跨分组，旧 Key 保存的 `cross_group_retry=false` 不会阻止切换；新建或修改智能 Key 时后端会保存为 `true`。手动和旧自动分组的配置语义保持兼容。

候选排序在一次请求中固定，保留用户可用范围、排除分组、模型能力及协议过滤。在当前分组中优先尝试尚未失败的渠道；多 Key 渠道可以继续使用尚未失败的凭证。相同上游、模型和凭证的渠道别名不会造成重复请求。无候选凭证、组内次数耗尽或当前渠道关闭重试时，推进到后面的候选分组。上限是允许的最大次数，不保证一定重试满 3 次。

重试规则不能绕过已输出响应、客户端取消、指定渠道、显式 `SkipRetry`、不可重试的响应体错误以及 `413/422` 等确定性请求错误。默认重试上游鉴权、容量和部分服务端错误；`400/408/504/524` 默认不重试，其他状态和显式恢复规则仍受上述保护及预算约束。

任务提交与可配置资源接口使用相同的保护和错误判断。任务提交网络错误、超时、已绑定原渠道的任务续作不重发。可配置资源按智能排名选择候选，已知任务/资源 ID、可能产生写入的前置请求和结果不明的写操作不跨上游重放，避免重复创建资源。任务接口的性能样本衡量提交阶段，不代表后台生成任务的完成耗时。

性能样本按上游尝试独立记录，失败后由备用分组完成的请求也会记录前面分组的失败。失败样本沿用现有统计口径：计入 `429`、服务端及网络错误，其他 `4xx` 不计入性能失败率。备用分组的延迟不包含之前失败尝试的时间；原始请求耗时仍保留在请求及计费日志中。错误日志的管理员信息包含 `smart_retry` 次数、分组用量和时间预算，不记录用于去重的凭证散列。
